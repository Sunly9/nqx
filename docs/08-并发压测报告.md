# 并发压测报告

> 验证目标：**并发下业务不变量是否成立**，而不是跑一个好看的 QPS 数字。
>
> 压测时间：2026-10-15 · 并发数 200 · 被测环境：JDK 17 / SpringBoot 3.5.16 /
> MySQL 8.0.42 / Redis 5.0.14 · 单实例部署

---

## 一、为什么压测的判据是「业务不变量」而不是 QPS

写并发测试时最容易走偏的地方，是把 QPS 当成结论。但 QPS 受机器配置、网络、
JVM 预热、连接池大小影响极大 —— 换一台机器数字就完全不同，
**它无法证伪任何东西**。

这个项目里真正需要被证明的是三件事：

| 不变量 | 如果实现错了会怎样 |
|---|---|
| **库存不会被扣成负数** | 100 件库存卖出 137 件，超卖的 37 件要么发不出货，要么平台自己贴钱 |
| **积分不会被扣成负数** | 用户用 1000 积分换走了价值 16000 积分的商品，**积分等同于平台负债** |
| **同一笔业务不会重复入账** | 网络重试或用户双击导致重复发积分，**且这类错误只能靠用户投诉发现** |

这三条的共同点是：**每一个请求都返回成功，但总量超出了上限。**
所以判据必须是"数据库里的最终数字 + 成功条数"，而不是响应码。

**压测脚本的设计也据此确定**：不追求极限压力，而是用 `Promise.all`
把 200 个请求**同时**发出（瞬时并发，而非持续压力）—— 这正是触发竞争条件的形状。

## 三、场景 A · 库存防超卖

**方法**：库存 100，200 个并发请求各买 1 件（4 个用户轮转）。

**期望**：恰好 100 个成功、100 个报「库存不足」，库存精确归零且永不为负。

### 接口侧结果

```
并发请求数 : 200
成功       : 100
业务失败   : 100
传输异常   : 0
耗时       : 2253 ms   → 吞吐约 89 req/s

失败原因分布：
  100 次  「CR2016 锂锰纽扣电池」库存不足
```

### 数据库侧核对

| 商品 | 剩余库存 | 累计销量 |
|---|---|---|
| CR2016（id=3） | **0** | **100** |

| 断言 | 结果 |
|---|---|
| 库存为负 | ❌ 未发生 ✅ |
| 库存精确归零 | ✅ 是（0） |
| 实际卖出件数（按订单明细统计） | **恰好 100 件** ✅ |

**结论**：**未发生超卖，库存精确归零。**

### 为什么能保证

库存扣减走的是**原子条件更新**：

```sql
UPDATE product
SET stock = stock - #{quantity}, sold_count = sold_count + #{quantity}
WHERE id = #{productId}
  AND stock >= #{quantity}
  AND deleted = 0
```

把「判断够不够」与「扣减」合并进同一条 SQL，由 InnoDB 行锁串行化执行，
扣不动的请求 `affectedRows = 0`，调用方据此抛业务异常并回滚整个事务。

**如果写成"先 SELECT 查库存 → 应用层判断 → 再 UPDATE"**，三步之间就是竞态窗口：
200 个请求会同时查到"还剩 1 件"，然后各扣一次，库存变成负数。
这类 Bug 在单线程自测时永远不会出现。

> **易被忽略的一点**：`AND stock >= #{quantity}` 这个条件参数容易写完就忘了检查返回值。
> **调用方必须判断 `affectedRows`，返回 0 时抛异常回滚** ——
> 忽略返回值是这套方案最常见的失效原因（SQL 本身没问题，但没人看结果）。

## 四、场景 B · 积分防超发（防超扣）

**方法**：用户 2 有 1000 积分，兑换品 80 积分/件，200 个并发兑换请求。

**期望**：恰好 12 个成功（12 × 80 = 960，第 13 个需要 1040 > 1000），余额剩 40 且永不为负。

### 接口侧结果

```
并发请求数 : 200
成功       : 12
业务失败   : 188
传输异常   : 0
耗时       : 2710 ms   → 吞吐约 74 req/s

失败原因分布：
  188 次  积分不足
```

### 数据库侧核对

| 用户 | 剩余积分 | 累计获得 | 累计消耗 | 累计获得 − 累计消耗 |
|---|---|---|---|---|
| 用户 2 | **40** | 1000 | 960 | **40** ✅ |

**三方对账**（订单、流水、积分三个口径必须一致）：

| 口径 | 数值 |
|---|---|
| 兑换订单数 | 12 |
| 扣分流水条数 | 12 |
| 共扣积分 | 960 |
| 商品 5 库存变化 | 1000 → 988（−12） |

**结论**：**未发生超发，且三个口径完全一致。**

### 为什么不能只看「最终余额 ≥ 0」

这是一个容易被忽略的判据陷阱：条件更新失败时事务会回滚，
**最终余额本来就是对的**。真正的风险在于"两个请求同时读到余额够、各扣一次" ——
那会表现为**成功条数超过理论值**（比如 13、14 次），而余额仍然可能显示正常。

所以判据必须是**成功条数恰好等于理论值**，而不是"余额没变负"。

### 为什么能保证

```sql
UPDATE points_account
SET balance = balance - #{points},
    total_spend = total_spend + #{points}
WHERE user_id = #{userId}
  AND balance >= #{points}
```

同一套"条件更新 + 检查 affectedRows"的思路。

另外积分变更前会用 `SELECT ... FOR UPDATE` 加行锁，目的是让流水里的
`balance_after`（变动后余额）算得准确 —— 否则两个并发事务会读到同一个旧余额、
各自算出一个"变动后余额"，其中一条必然对不上账。

## 五、场景 C · 接口幂等

**方法**：200 个并发请求带**同一个** `request_id` 调用管理员调整积分接口。

**期望**：全部返回成功（幂等语义），但流水表**只新增 1 条**、余额只加一次。

### 接口侧结果

```
并发请求数 : 200
成功       : 200      ← 全部成功，符合幂等语义
业务失败   : 0
传输异常   : 0
耗时       : 2333 ms   → 吞吐约 86 req/s
```

### 数据库侧核对

| 幂等键 | 变动类型 | 变动值 | 变动后余额 | **同幂等键条数** |
|---|---|---|---|---|
| `ADJUST-loadtest-1792080417751` | 6（管理员调整） | 7 | 107 | **1** ✅ |

用户 3 的余额：100 → 107（只加了一次 7）。

**结论**：**200 次并发只入账 1 条，幂等成立。**

### 为什么"全部返回成功"是对的

真正的幂等语义不是"重复请求要报错"，而是**"重复请求的结果与第一次相同"**。
调用方（管理后台）在网络抖动后重试，应当拿到成功响应而不是一个错误 ——
否则前端会提示"操作失败"，而实际上操作早已生效，用户会再点一次。

所以实现上是：捕获 `DuplicateKeyException` 后**按幂等成功处理**，返回当前余额。

### 为什么应用层判断必然失效

```
线程 A：查有没有处理过 → 没有
线程 B：查有没有处理过 → 没有      ← 两个线程都查到"没有"
线程 A：插入流水 → 成功
线程 B：插入流水 → 成功            ← 重复入账
```

应用层的"先查再插"在并发下**必然**失效。唯一可靠的防线是数据库唯一索引：

```sql
UNIQUE KEY uk_user_biz_type (user_id, biz_no, change_type)
```

**关键点**：`biz_no`（业务单号）就是幂等键。要让这套机制生效，
调用方必须为"同一笔业务"传相同值 —— 所以管理端调整积分的接口
把 `request_id` 设计成**由调用方生成**的参数，而不是服务端自己编一个。

> **把 `change_type` 也纳入唯一索引**是有意为之：一笔兑换业务（`biz_no` 相同）
> 先扣分（type=4），后续若发生退款（type=5），两者是两笔合法的独立流水。
> 若只用 `(user_id, biz_no)`，退款就永远记不进去。

## 六、全局兜底检查

```
库存为负的商品数         : 0
积分为负的账户数         : 0
账目不自洽的账户数       : 0     ← total_earn − total_spend <> balance
```

「账目自洽」这一项值得单独说：`total_earn` 与 `total_spend` 表面上只是给用户看的统计，
但它们实际上是**账目的校验位**。只要始终满足
`balance = total_earn − total_spend`，就说明所有积分变动都经过了统一入口；
一旦不等，就一定存在某处绕过了记账逻辑直接改了余额 ——
而这类问题不查这两个字段是发现不了的。

## 八、结论与局限

### 结论

| 不变量 | 结果 |
|---|---|
| 库存不被扣成负数、不超卖 | ✅ 200 并发下恰好卖出 100 件，库存精确归零 |
| 积分不被扣成负数、不超发 | ✅ 200 并发下恰好成功 12 次，余额剩 40，三方对账一致 |
| 同一笔业务不重复入账 | ✅ 200 并发只入账 1 条 |
| 账目始终自洽 | ✅ `balance = total_earn − total_spend` 全部成立 |

### 局限（如实说明）

1. **单实例、单机压测**。多实例部署下的并发行为未覆盖 ——
   不过这三处防线（行锁、唯一索引、条件更新）都在数据库侧，
   应用多实例不会改变它们的正确性。
2. **瞬时并发而非持续压力**。本文验的是"竞争条件是否被正确处理"，
   不是"系统能扛多少 QPS"。89 / 74 / 86 req/s 是**本机单实例**在
   2 秒左右窗口内的吞吐，**不能当作容量指标引用** ——
   若要测容量，应使用 wrk/JMeter 做固定时长的持续压测，
   并配合连接池、GC、慢查询日志一起分析。
3. **未做故障注入**。例如 MySQL 在事务中途不可用、Redis 抖动等场景未覆盖。
4. 压测在开发库上执行，**已产生 112 笔真实订单**（100 笔采购 + 12 笔兑换）。
   这是有意保留的 —— 请对照 `scripts/load-test-verify.sql` 的输出核对，
   而不是只相信我在这里写的结论。
