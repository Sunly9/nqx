# 小程序端改造方案

> 本文基于对旧版小程序源码（`E:\纽启新生app\app1`）的实际阅读写成，
> 所有结论都出自代码，不是推测。

## 二、旧版的问题（本次重构要解决的）

### 2.1 表结构按角色整套复制（最严重）

```
回收方                          采购方
users                    ←→   procurement_users
orders                   ←→   procurement_orders
addresses                ←→   procurement_addresses
points_history           ←→   procurement_points_history
faqs                     ←→   procurement_faqs
exchange_goods / procurement_goods / procurement_products
```

20 张表里 **10 张是重复的**。后果：

- 一个人若既是回收方又是采购方（实验室账号完全可能如此），
  他的**积分、地址、订单分散在两套表里**，无法统一展示与统计；
- 任何"查这个用户的所有订单"的需求都要查两张表再合并；
- 新增一个字段要改两处，迟早不一致。

**新设计的处理**：`app_user` + `app_user_role`（多对多身份）、`biz_order` + `order_type`
（统一订单主表）、`user_address`、`points_account` + `points_record` 全部单套表。
表数量没有膨胀，却把"一个用户两种身份"表达清楚了。

### 2.2 管理端接口暴露在小程序 API 上，且完全没有鉴权

```js
app.post('/api/points/goods', ...)      // 新增积分商品
app.put('/api/points/goods/:id', ...)   // 修改积分商品
app.delete('/api/points/goods/:id', ...)// 删除积分商品
```

这三个是**运营管理操作**，却直接挂在面向小程序的 `/api/*` 上。
任何人拿到接口地址就能增删改积分商品。
新设计里它们只存在于 `/admin/**`，受 RBAC 权限码 `product:add` 等保护。

### 2.3 所有接口靠 `user_id` 参数识别用户 → 水平越权

```js
app.get('/api/orders/list', async (req, res) => {
  const { user_id } = req.query;               // ← 用户身份来自查询参数
  const [rows] = await db.query('SELECT * FROM orders WHERE user_id = ?', [user_id]);
```

只要把 `user_id` 改成别人的，就能看到别人的订单、地址、积分。
新设计改为从 Sa-Token 会话中取当前用户 ID，**请求参数里的 user_id 一律忽略**。

### 2.4 结算逻辑没有事务

```js
// /api/orders/settle 里连续三条 SQL，无事务包裹
await db.query('UPDATE orders SET status=?, weight=?, points_earned=? WHERE id=?', ...);
await db.query('UPDATE users SET points=points+?, total_weight=total_weight+? WHERE id=?', ...);
await db.query('INSERT INTO points_history (...) VALUES (...)', ...);
```

中间任意一步失败（或进程重启），就会产生**订单已结算但积分没到账**，
或**积分已加但流水缺失**的不一致状态。
新设计用 `@Transactional(rollbackFor = Exception.class)` 包裹全部三步。

### 2.5 重复结算防护不可靠

虽然检查了 `if (order.status === 'completed') return 400`，
但"检查"与"更新"之间没有任何原子性或锁。两个并发请求可以同时通过检查、
各加一次积分。新设计靠 **`points_record` 的唯一索引 `
(user_id, biz_no, change_type)`** 从数据库层面兜底，应用层判断只是第一道防线。

### 2.6 业务参数硬编码

```js
const pointsEarned = Math.floor(actual_weight * 100);   // 1kg = 100 积分
const carbonSaved = (actual_weight * 0.5).toFixed(2);   // 系数 0.5
```

改个回收单价要改代码、重新部署。新设计放进 `site_setting` 表（KV 结构），
运营可自助调整。

### 2.7 ⚠️ 真实凭证明文提交进了代码库

`server/.env` 中包含：

| 项 | 风险 |
|---|---|
| 腾讯云 MySQL 的 **root 账号与密码** | 拿到即可读写整个数据库实例 |
| 微信 **AppSecret** | 拿到即可冒充你的小程序调用微信接口（获取用户信息、发订阅消息、支付） |

**这两项必须立即处理**：

1. 到微信公众平台 **重置 AppSecret**（旧的那个已经泄露，无论是否已提交到公开仓库）；
2. 修改腾讯云数据库的 root 密码，或直接改用最小权限账号；
3. 把 `.env` 加入 `.gitignore`，仓库里只留 `.env.example`；
4. **如果这个仓库曾经推送到过任何公开/半公开的位置，视为凭证已完全泄露**，
   仅靠删除文件是不够的 —— Git 历史里还在。

> 本项目的 `.gitignore` 已经把 `.env`、`*.pem`、`*.jks` 等排除在外，
> 并且 `docker-compose.yml` 用的是环境变量而非明文配置。

## 三、改造策略：兼容垫片

### 3.1 问题

旧版 27 个页面里，每一处请求都长这样：

```js
wx.cloud.callContainer({
  env: 'your-cloudrun-env-id',
  service: 'app',
  path: '/api/orders/list',
  method: 'GET',
  data: { user_id: 1 },
  success: (res) => { const list = res.data.orders; ... },
  fail: (err) => { ... }
});
```

逐页手改成 `wx.request` 需要动 27 个文件、几十处调用点，
而且每一处都要记得加 `Authorization` 头、都要解包新的返回体 —— 极易漏改。

### 3.2 方案

保留 `callContainer` 这个**调用形状**，只替换它的**实现**：

```js
// nqx-miniprogram/utils/request.js
wx.cloud.callContainer = function (opts) {
  request({ url: opts.path, method: opts.method, data: opts.data })
    .then(payload => opts.success && opts.success({ statusCode: 200, data: payload }))
    .catch(err => opts.fail && opts.fail(err));
};
```

在 `app.js` 的 `onLaunch` 最前面调用一次 `installCloudShim()`，
此后**页面代码一行都不用改**，请求就会打到 SpringBoot 后端。

垫片同时负责：

- 拼接 `env.API_BASE_URL`
- 注入 `Authorization: Bearer <token>`
- 解包 `Result<T>`，把 `body.data` 放到页面期望的 `res.data`
- 401 时静默重登并**自动重放原请求**

### 3.3 代价（必须承认）

- 这是**猴子补丁**，覆盖了平台 API，语义上不够干净；
- 新写的页面应直接使用 `request.get/post`，不要再走垫片；
- 垫片是过渡层，页面迁移完成后应当删除。

这是"用一点显式技术债换大量改造工时"的取舍。**债要标出来，不能装作不存在。**

## 七、执行步骤（给你的操作清单）

1. **先做安全整改**（见 §2.7）—— 重置 AppSecret 与数据库密码，优先级最高。
2. 把旧项目的 `pages/`、`components/`、`custom-tab-bar/`、`assets/`
   拷贝到本项目的 `nqx-miniprogram/` 下（本目录已提供改造好的 `app.js` 与 `utils/`）。
3. 删除 `utils/mock.js` 与 `utils/env.js` 的旧内容（已用新版覆盖）。
4. 搜索全局残留的 `wx.cloud.init`，删掉（`app.js` 已处理，页面里应该没有）。
5. 微信开发者工具 → 详情 → 本地设置 → 勾选**「不校验合法域名」**。
6. 逐页验证；对新写的页面直接用 `require('../../utils/request')`。
7. 全部页面迁移完成后，删除 `installCloudShim()` 与其调用。
