# 核心组件设计说明

> 本文说明三个横切组件的设计取舍：`@Log` 操作日志、`@Idempotent` 接口幂等、
> `RedisCacheService` 逻辑过期缓存。它们都是「业务无关的基础设施」，
> 做好之后每个业务接口只需加一行注解。

---

## 一、`@Log` 操作日志

代码位置：`nqx-common/.../annotation/Log.java`、`nqx-web/.../aspect/LogAspect.java`、
`nqx-service/.../system/OperationLogRecorder.java`

### 1.1 为什么落库必须异步，且必须拆成独立的 Bean

`@Async` 依赖 Spring AOP 代理生效，而**代理只对「从外部调用」的方法生效**。
如果把异步方法写在切面内部并直接 `this.record(...)` 调用：

```java
// ✗ 错误：自调用绕过代理，方法体同步执行，"异步"完全失效且不报错
@Around("@annotation(log)")
public Object around(ProceedingJoinPoint p) {
    ...
    this.record(entity);   // 同步执行！
}
```

这不会抛任何异常，只是每次写日志都同步多一次数据库 IO，拖慢主流程 ——
**是 `@Async` 最经典的失效场景，也最难被发现**。

因此拆出独立的 `OperationLogRecorder`，切面通过注入调用，走的才是代理对象。

### 1.2 为什么切面必须原样抛出异常

```java
try {
    return point.proceed();
} catch (Throwable e) {
    entity.setStatus(0);
    throw e;      // ← 必须抛出
} finally {
    recorder.record(entity);   // ← 必须放 finally
}
```

若用 `return null` 代替抛出，会造成三重连锁故障：

1. `GlobalExceptionHandler` 收不到异常，前端拿到 `code=200` 却没有任何数据；
2. `@Transactional` 感知不到异常，**该回滚的事务照常提交**；
3. 排查时看到的是一条"成功"日志，与事实相反。

而放 `finally` 是为了让失败的尝试也留下记录 —— 失败的尝试恰恰是审计重点
（谁在反复越权？谁在暴力试密码？）。

### 1.3 脱敏：为什么用 Jackson 遍历而不是正则替换

操作日志会把接口入参完整落库。若不脱敏，`sys_operation_log` 就会成为
全系统最大的一处明文数据泄露点：重置密码的请求体里带着新密码、
小程序登录带着手机号、绑定微信带着 openid。

**正则处理 JSON 极易出错**：字段值本身可能包含引号、转义符、嵌套的 JSON 字符串，
处理不当要么漏脱敏（安全问题），要么把 JSON 改坏（日志不可读）。

实现改为先把参数转成 `JsonNode` 树，再按字段名递归遍历：

```java
JsonNode root = objectMapper.valueToTree(value);
mask(root);                          // 递归：命中敏感字段名则打码
return objectMapper.writeValueAsString(root);
```

实测效果（真实从数据库查出的记录）：

```json
{"dto":{"username":"admin","password":"****"}}
```

手机号、openid 这类需要保留部分字符的字段，单独按"保留前 N 位"处理。

### 1.4 身份采集的时序陷阱（这个坑很隐蔽）

采集"是谁操作的"看似简单，实际有**两个方向相反的时序要求**：

| 接口 | 执行前 | 执行后 | 正确取值 |
|---|---|---|---|
| 登录 | `anon`（会话尚未建立） | `admin` | **执行后** |
| 注销 | `admin` | `anon`（会话已销毁） | **执行前** |
| 普通接口 | `admin` | `admin` | 均可 |
| 登录失败 | `anon` | `anon` | `anon`（符合事实） |

**只取执行前**：登录日志的操作人永远是 `anon`。
**只取执行后**：注销日志的操作人永远是 `anon`，丢失了"谁注销的"最关键信息。

解法是两次都采集，取"执行后拿得到就用执行后，拿不到就回退到执行前"：

```java
Identity identityBefore = Identity.capture();   // 执行前
try { ... } finally {
    Identity identityAfter = Identity.capture(); // 执行后
    Identity actor = identityAfter.isAnonymous() ? identityBefore : identityAfter;
    actor.applyTo(entity);
}
```

用 `record Identity` 把「用户类型 + 用户 ID + 用户名」作为一个整体比较与回退，
避免出现"类型用了执行前的、用户名用了执行后的"这种自相矛盾的日志。

## 二、`@Idempotent` 接口幂等

代码位置：`nqx-common/.../annotation/Idempotent.java`、`nqx-web/.../aspect/IdempotentAspect.java`

### 2.1 为什么用 SETNX 而不是「先 GET 再 SET」

```java
// ✗ 有竞态窗口：两个并发请求可能同时 GET 到 null，然后都 SET 成功
if (redis.get(key) == null) { redis.set(key, "1"); /* 放行 */ }

// ✓ 单条命令、Redis 单线程串行执行，天然原子
redis.opsForValue().setIfAbsent(key, "1", Duration.ofSeconds(expire));
```

### 2.2 三个决定成败的细节

| 细节 | 不做的后果 |
|---|---|
| **业务失败必须释放 Key** | 用户输错参数后，在过期时间内连改都改不了。这是幂等实现里最影响体验的错误 |
| **必须有合理的过期时间** | 某次请求异常终止没走到释放逻辑，该用户将**永久**无法再调用此接口，只能等重启 |
| **Key 必须包含用户维度** | A 提交成功后 B 也被拦截。**这个错误在单人测试时完全发现不了** |

Key 结构：`nqx:idempotent:<业务前缀>:<业务键>`

- `prefix` 未指定时退化为「类名:方法名」，保证不同接口不互相干扰；
- 业务键默认取「端前缀 + 登录 ID」，如 `admin:1` / `app:5`。
  **端前缀不可省**：`sys_user.id = 1` 与 `app_user.id = 1` 是两个人。

### 2.3 SpEL 的安全边界（必须知道）

`StandardEvaluationContext` 允许表达式调用任意静态方法，例如
`T(java.lang.Runtime).getRuntime().exec(...)` —— 这是 RCE。

本项目中的表达式全部来自**开发者手写的注解**，不涉及用户输入，因此安全。
**但绝不能把用户可控的字符串当作 SpEL 表达式解析。** 这是使用 SpEL 时的铁律。

另外：表达式解析失败时会**显式抛异常**，而不是静默退化成一个共用 Key ——
静默退化会让所有用户共用一个幂等 Key，把正常用户全部拦掉，
这种故障比直接报错严重得多。

### 2.4 切面顺序

| 切面 | Order | 理由 |
|---|---|---|
| `LogAspect` | `HIGHEST_PRECEDENCE + 10` | 更外层，能记录到幂等拦截抛出的异常 |
| `IdempotentAspect` | `HIGHEST_PRECEDENCE + 20` | 更内层 |

```
请求 → TraceIdFilter → SaToken 拦截器 → LogAspect → IdempotentAspect → Controller
```

这样「谁在重复提交」这个值得审计的行为也会被记录下来。

## 三、`RedisCacheService` 逻辑过期缓存

代码位置：`nqx-service/.../cache/RedisCacheService.java`

### 3.1 解决什么问题

普通的 TTL 缓存存在**缓存击穿**：热点 Key 过期的那一瞬间，
所有并发请求同时发现缓存没了，一起涌向数据库。
QPS 5000 的热点 Key 每秒过期一次，数据库就要承受一次 5000 并发冲击。

**逻辑过期的核心**：物理上不设（或设很长的）TTL，过期时间写在**缓存值内部**。
于是 Key 永不真正消失，读取时：

```
值存在且未逻辑过期  → 直接返回
值存在但已逻辑过期  → ① 立刻把旧值返回给当前请求
                      ② 尝试抢互斥锁，抢到的线程【异步】重建缓存
值不存在           → 同步查库并回填（首次访问 / Redis 被清空）
```

**收益：任何时刻都不会出现「大量请求同时打数据库」。**
逻辑过期瞬间所有请求都立刻拿到（稍旧的）数据，只有抢到锁的那一个线程去查库，
而且是在后台线程里做，不阻塞用户请求。

### 3.2 三种方案的取舍（面试常问）

| 方案 | 一致性 | 可用性 | 适用场景 |
|---|---|---|---|
| TTL + 互斥锁重建 | 较高 | 重建期间请求被阻塞 | 数据量小、重建快 |
| **逻辑过期（本项目）** | 最终一致 | 不阻塞，始终有数据 | **热点数据、重建耗时** |
| 定时任务预热 | 取决于周期 | 无重建延迟 | 数据量有限、可枚举 |

**代价必须主动说出来**：逻辑过期期间返回的是旧数据。
商品详情这种"改价后晚几秒生效也能接受"的场景没问题，
但**库存、余额这类数据绝不能使用这套缓存**。

### 3.3 缓存三兄弟的完整防护

| 问题 | 现象 | 本实现 |
|---|---|---|
| **穿透** | 查不存在的数据，请求全打到库 | **空值哨兵** `__NQX_NULL__`，TTL 仅 60 秒 |
| **击穿** | 热点 Key 过期瞬间大量请求打库 | **逻辑过期 + 互斥锁异步重建** |
| **雪崩** | 大量 Key 同时过期 | 过期时间叠加**随机偏移** `randomExpireSeconds` |

空值缓存的 TTL 刻意设得很短（60 秒），因为"不存在"这个结论可能很快失效
（数据被创建出来了）。用长 TTL 会导致"新增了数据却查不到"的诡异现象。

### 3.4 一致性策略与它的残留缺陷

采用 Cache-Aside 的「**先更新数据库，再删除缓存**」，而不是更新缓存 ——
因为更新缓存会引入并发写覆盖：两个线程分别更新库和缓存，顺序交错时缓存里会留下旧值。

**这套策略的残留缺陷（要能主动说出来）**：若"删除缓存"这一步失败
（网络抖动、Redis 短暂不可用），缓存里就会长期残留旧数据。

工业界的补救手段：
1. **延迟双删** —— 更新后延迟几百毫秒再删一次；
2. **订阅 binlog 异步删除**（Canal）—— 从数据库层面保证不遗漏。

本项目为控制复杂度未引入，依靠逻辑过期时间兜底（最长 30 分钟一定刷新）。
**能主动指出自己方案的不足，比声称方案完美更能拿分。**
