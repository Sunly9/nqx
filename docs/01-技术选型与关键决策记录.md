# 技术选型与关键决策记录

> 本文档记录**为什么这么选**。具体锁定的版本号见 [`04-依赖版本锁定.md`](04-依赖版本锁定.md)。

---

## 1. 为什么从 Node.js 换成 SpringBoot

原项目是 Node.js 实现，功能是通的，但作为求职作品存在三个硬伤：

| 问题 | 说明 |
|---|---|
| 与目标岗位不匹配 | 国内后端岗位绝大多数要求 Java 技术栈，Node.js 项目无法证明 Java 工程能力 |
| 缺少可深挖的技术难点 | CRUD 型 Node 项目很难讲出「并发、幂等、缓存一致性、事务」这类面试核心考点 |
| 无法体现工程化 | 没有分层架构、统一异常、权限模型、数据库版本管理等企业级工程实践 |

换 Java 的直接收益：**SpringBoot 的事务、AOP、MyBatis 动态 SQL、Sa-Token 权限模型**，每一个都是国内后端面试的必考项，且都能在这个项目里找到真实落地场景。

## 2. JDK 版本：为什么是 17，绝不能是 18

| 版本 | 类型 | 状态 | 结论 |
|---|---|---|---|
| JDK 8 | LTS | 已过主流支持期 | SpringBoot 3.x 不支持，排除 |
| JDK 11 | LTS | 维护中 | SpringBoot 3.x 不支持（3.x 要求 17+），排除 |
| **JDK 17** | **LTS** | **长期支持至 2029+** | ✅ **选它** |
| JDK 18 | 非 LTS | **2022-09 已停止支持** | ❌ 绝对不能用 |
| JDK 21 | LTS | 维护中 | 技术上可行，但三方库适配不如 17 充分 |
| JDK 26 | 非 LTS | 短周期版本 | ❌ 生产项目禁用 |

**关于 JDK 18 的明确结论**：JDK 18 是 Oracle 的**非 LTS 短周期版本**，2022 年 3 月发布、**2022 年 9 月就结束了官方支持**，生命周期只有 6 个月。它比 JDK 21 更不稳定——因为：
1. 已经停止接收安全补丁；
2. 大量三方库（MyBatis-Plus、Sa-Token、Knife4j 等）的测试矩阵只覆盖 LTS 版本，从未针对 18 做过验证；
3. 它引入的一些特性在 19/20 中又被调整，属于"过渡版本"。

**所以：需求里的"JDK 17 或 18"，正确答案只有 17。**

**为什么选 17 而不选 21？**
JDK 17 是 SpringBoot 3.x 的**最低基线版本**，意味着所有三方库都必须保证在 17 上可用——它天然是兼容性测试覆盖最广的版本。JDK 21 虽然也是 LTS，但部分依赖（尤其是字节码增强类库）在 21 上的适配问题暴露得晚、修复得慢。**"最稳"的工程含义就是：选生态验证最充分的那个版本，而不是最新的那个。**

## 3. SpringBoot 版本：3.5.x

| 版本线 | 判断 |
|---|---|
| 2.7.x | 已停止开源维护，且用的是 `javax.*` 包名，与主流教程脱节，排除 |
| **3.5.x** | ✅ **3.x 的最后一条线，生态适配最完整、补丁最全** |
| 4.x | 太新，三方库（尤其是接口文档、权限框架）适配滞后，排除 |

选 3.5.x 而不是 4.x 的理由很直白：**这个项目的价值在于「能跑通 + 能讲透」，不在于「用最新版本」。** 用 4.x 换来的是可能踩不完的兼容性坑——比如接口文档组件、权限框架尚未适配 Spring Framework 7，会白白消耗掉本该用来做核心难点的时间。

**注意包名迁移**：SpringBoot 3.x 用的是 `jakarta.*` 而非 `javax.*`。网上大量 SpringBoot 2.x 的代码示例直接抄会编译不过（`javax.servlet.http.HttpServletRequest` → `jakarta.servlet.http.HttpServletRequest`）。这是新手迁移 3.x 最常见的坑。

## 4. 持久层：MyBatis-Plus + 手写 XML

| 方案 | 判断 |
|---|---|
| 裸 MyBatis | 单表 CRUD 要手写大量 XML 样板，浪费时间 |
| JPA / Hibernate | 复杂动态查询（后台多条件检索）用 Criteria API 极其别扭，且国内岗位以 MyBatis 为主 |
| **MyBatis-Plus + 手写 XML** | ✅ **单表 CRUD 用 MP 提效，复杂查询手写 XML 保持 SQL 可控** |

**关于"简历写 MyBatis 是否算虚假"**：不算。MyBatis-Plus 是 MyBatis 的增强工具，底层仍是 MyBatis，项目里手写 XML 的部分就是标准 MyBatis 用法。

**面试怎么答"为什么用 MyBatis-Plus"**：
> 单表的增删改查、分页、逻辑删除这类重复劳动交给 MP 自动生成，能省掉 60% 的样板代码；但后台订单的多条件组合检索、看板的聚合统计这类复杂 SQL，我坚持手写 XML——因为 MP 的 Wrapper 在多层嵌套条件和聚合函数下可读性会急剧下降，而且 SQL 不透明，出问题难以定位。**提效的地方用工具，需要控制力的地方自己写。**

## 5. 权限框架：Sa-Token

| 方案 | 判断 |
|---|---|
| Spring Security | 功能最全、大厂主流，但配置复杂，学习成本会挤占核心业务的时间 |
| **Sa-Token** | ✅ **API 简洁，双端登录、踢人下线、权限注解开箱即用** |

Sa-Token 完全够用，但**关键在于要把 RBAC 做扎实**，而不是只做认证：

- ❌ 减分做法：`if (role.equals("ADMIN")) { ... }` —— 角色硬编码在业务代码里
- ✅ 加分做法：`用户 → 角色 → 权限(目录/菜单/按钮)` 三级模型，权限码落库，用 `@SaCheckPermission("order:recycle:audit")` 注解 + AOP 校验，前端拿权限码做按钮级控制

**必须解决的技术点：小程序端和管理端是两套登录体系**

| | 小程序端 | 管理端 |
|---|---|---|
| 认证方式 | `code` 换 openid | 账号 + 密码 |
| 用户表 | `app_user` | `sys_user` |
| Token 前缀 | `Authorization: Bearer <token>` | 同左，但校验时区分登录类型 |

**方案**：使用 Sa-Token 的**多账号体系**（自定义 `StpLogic`，如 `StpAdminUtil` / `StpAppUtil`），两套体系各自独立管理 token、互不干扰。**这是这个项目里最容易被面试官问穿的点，必须做对。**

## 6. 缓存与并发：Redis

Redis 不是"用了就行"，要落到具体场景：

| 场景 | 用法 | 面试价值 |
|---|---|---|
| 商品热点缓存 | Cache-Aside + 逻辑过期 + 互斥锁 | 缓存三兄弟必问 |
| 登录会话 | Sa-Token 集成 Redis，支持多实例共享会话 | 说明"为什么不能放本地内存" |
| 订单超时取消 | ZSet 延迟队列 + Lua 原子出队 | **强亮点** |
| 接口幂等 | `SETNX` + 过期时间 | 高频考点 |
| 积分排行榜 | ZSet | 小而美 |
| 问答接口限流 | 滑动窗口 / 令牌桶 | 防刷，实用 |

**不引入的东西及理由**：
- **不引 MQ（RocketMQ/RabbitMQ）**：订单超时用 Redis ZSet 已足够，且可以顺手讲清"延迟消息的三种实现（定时扫描 / ZSet / MQ 死信）及各自取舍"。硬上 MQ 但讲不清消息丢失、重复消费、顺序性，反而扣分。
- **不引分布式锁框架 Redisson（初版）**：先用「唯一索引 + 条件更新」这种更轻的幂等方案，把原理讲透；Redisson 作为"如果竞争更激烈会怎么升级"的延伸答案。

## 7. 订单建模：回收单与采购单统一

详见 [`02-数据库设计说明.md`](02-数据库设计说明.md#34-交易订单-3-张--购物车--地址)。核心结论：

- **统一主表** `biz_order` + `order_type` 区分，好处是后台检索、导出、看板统计、流转日志**一套代码覆盖两类业务**；
- **状态机分开**，用策略模式按 `order_type` 分发，好处是两类业务的差异被清晰隔离，不会写出满屏 `if (orderType == 1)`；
- **明细存快照**，保证历史订单不可篡改。

## 8. 明确不做的技术（避免堆栈式简历）

| 不做 | 理由 |
|---|---|
| Nacos / Gateway / 微服务拆分 | 单体足够。上了微服务却讲不清服务治理，是典型的"堆技术栈"减分项 |
| ShardingSphere 分库分表 | 没有真实数据量支撑，讲不出分片键选择依据就是空谈 |
| Seata 分布式事务 | 单库单服务，引入它属于自找麻烦 |
| ElasticSearch | 商品搜索用 `LIKE` + 索引完全够用，量级远不到 |
| 真实微信支付 | 需求明确为模拟结账；保留 `pay_type` 字段与 `PayService` 接口作为扩展点 |

**判断标准**：一项技术如果不能在面试里讲清「它解决了什么问题、我为什么在几个方案里选它、它的代价是什么」，就不该出现在简历上。

## 9. 工程分层与包结构

### 9.1 分层原则

```
Controller  →  只做「参数校验 + 调 Service + 包装返回」，不写业务逻辑
Service     →  业务逻辑、事务边界、缓存读写、幂等控制
Mapper      →  只做数据访问，复杂 SQL 写在 XML
Entity/DTO/VO → Entity 对应表，DTO 接收入参，VO 返回出参，三者严格分离
```

**为什么 Entity 不能直接返回给前端**：`sys_user` 里有 `password` 字段，直接返回就是泄露；`app_user` 里有 `openid`，不该暴露给前端。**DTO/VO 分离是安全边界，不是形式主义。**

### 9.2 Maven 多模块

```
nqx-parent
├── nqx-common      通用：Result、错误码、业务异常、全局异常处理、工具类、常量、注解
├── nqx-pojo        实体与传输对象：entity / dto / vo / query
├── nqx-mapper      数据访问：Mapper 接口 + XML
├── nqx-service     业务逻辑：Service 接口 + 实现 + 状态机 + 缓存 + 幂等
├── nqx-web         启动模块 + Web 配置（拦截器、Swagger、跨域、线程池）
└── nqx-admin       (可选) 管理端接口，随 nqx-web 启动
```

**依赖方向单向**：`web → service → mapper → pojo`，`common` 被所有模块依赖。**禁止反向依赖**（service 不能依赖 web），否则会形成循环依赖，Maven 直接构建失败。

## 10. 工程化清单（这些细节最能体现「像工作过的人」）

| 项 | 做法 |
|---|---|
| 统一返回 | `Result<T> { code, msg, data, timestamp }` |
| 全局异常 | `@RestControllerAdvice` 统一捕获，业务异常返回业务码，未知异常返回 500 且**不泄露堆栈** |
| 错误码 | 枚举集中管理（如 `ErrorCode.ORDER_STATUS_ILLEGAL(3001, "订单状态不允许该操作")`），禁止散落魔法字符串 |
| 参数校验 | `jakarta.validation` 的 `@Valid` + 分组校验，不手写 if 判断 |
| 链路追踪 | `OncePerRequestFilter` 生成 `traceId` 存入 MDC，logback 输出，异步线程用 `TaskDecorator` 传递 |
| 操作日志 | `@Log` 注解 + AOP + `@Async` 异步落库，**入参脱敏**（password/phone 打码） |
| 接口文档 | Knife4j / springdoc，本地开发必备 |
| 数据库版本管理 | Flyway，DDL 纳入 Git，杜绝「手工改生产库」 |
| 逻辑删除 | MyBatis-Plus `@TableLogic` 统一处理 |
| 分页 | 统一 `PageResult<T>` 封装，前端不用关心底层分页实现 |
| 配置分离 | `application-dev.yml` / `application-prod.yml`，敏感信息走环境变量 |
| 线程池 | 显式定义 `ThreadPoolTaskExecutor`（核心数/队列/拒绝策略），**禁止用 `Executors.newFixedThreadPool`**（无界队列会 OOM） |
| 容器化 | Docker Compose 一键起 MySQL + Redis + 应用 + Nginx |

## 11. 关键决策速查表

| 决策点 | 选择 | 一句话理由 |
|---|---|---|
| JDK | 17 (LTS) | SpringBoot 3.x 基线版本，生态验证最充分；18 已 EOL |
| 框架 | SpringBoot 3.5.x | 3.x 最后一条线，补丁最全，三方适配最完整 |
| 持久层 | MyBatis-Plus + 手写 XML | 提效与 SQL 可控兼得 |
| 权限 | Sa-Token 多账号体系 | 双端登录隔离，注解式鉴权 |
| 缓存 | Redis (Cache-Aside) | 覆盖缓存、延迟队列、幂等、排行、限流五大场景 |
| 消息队列 | 不引，用 Redis ZSet | 量级不到，且能把延迟消息原理讲透 |
| 订单建模 | 统一主表 + 分离状态机 | 一套检索/统计，差异用策略模式隔离 |
| 金额类型 | `INT` 存分 | 避免浮点误差 |
| 表名 | `biz_order` | 避开 MySQL 保留字 `ORDER` |
| 架构 | 单体多模块 | 单体足够，避免堆技术栈 |
| 支付 | 模拟结账 | 需求明确，保留扩展点 |
