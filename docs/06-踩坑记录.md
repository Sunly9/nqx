# 开发踩坑与故障排查记录

> 本文记录项目开发过程中**真实遇到并解决**的问题。
> 每一条都是「编译能通过、但运行会坏」或「代码看起来对、但数据是错的」这类
> 最难排查的问题。面试时可以挑其中几条讲，比泛泛而谈"我做过一个项目"有说服力得多。

## 一、依赖与兼容性（编码前就能避免的坑）

### 1. Knife4j 在 Spring Boot 3.5 上是硬性不兼容

**现象**：应用启动时报

```
java.lang.NoSuchMethodError:
  'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'
```

**注意这是运行期错误，不是编译期** —— `mvn compile` 会成功，启动时才炸。

**根因**：读 `knife4j-4.5.0.pom` 的 parent 发现它把
`knife4j-springdoc-openapi-jakarta.version` 硬锁在 `2.3.0`。
springdoc 2.3.0 早于 Spring Framework 6.2，而 Boot 3.5.16 用 6.2.19，
`ControllerAdviceBean` 的构造器签名变了。Knife4j 4.5.0 是 2024-01 的末版，官方无修复。

**解决**：改用 `springdoc-openapi-starter-webmvc-ui:2.8.17`
（其 parent 就是 `spring-boot-starter-parent:3.5.13`，官方验证过的组合）。

**网上的"绕过方案"不要用**：排除 springdoc 后单引 2.8.x + `knife4j.enable=false`，
虽然能启动，但 Knife4j 的**文档访问密码验证会被一并绕过**，等于把接口文档裸奔。

### 2. MyBatis-Plus 3.5.9+ 把 JSQLParser 拆成了独立依赖

**现象**：分页查询运行时抛 `NoClassDefFoundError: net/sf/jsqlparser/...`，编译期无任何提示。

**根因**：MyBatis-Plus 自 3.5.9 起把 JSqlParser 从核心包剥离为可选依赖。
直接读 `mybatis-plus-spring-boot3-starter:3.5.16` 的 pom 可以确认它**不再包含** JSQLParser。

**解决**：显式引入 `com.baomidou:mybatis-plus-jsqlparser:3.5.16`。

### 3. `sa-token-redis-jackson` 是个空 jar

**现象**：向 `sa-token-redis-jackson-1.44.0.jar` 里查类，发现**一个 class 都没有**，
只有 `META-INF` 元数据。

**影响**：如果不查证就以为"已经接入 Redis 会话存储"，实际 Sa-Token 会静默回退到
内存存储（`SaTokenDaoDefaultImpl`），**多实例部署时登录态不共享**
——用户登录后被负载均衡打到另一台机器就变成未登录。这是一个不会报错的功能缺失。

**真相**：它是聚合 POM，真正实现在传递依赖里：

```
sa-token-redis-jackson
├── sa-token-jackson          （会话对象的 Jackson 序列化）
└── sa-token-redis-template   （真正的 DAO：SaTokenDaoForRedisTemplate）
```

**顺带的重要发现**：`SaTokenDaoForRedisTemplate` 用的是 **`StringRedisTemplate`**
而不是 `RedisTemplate<String,Object>`。因此本项目**不应**再自建 `RedisTemplate` Bean
—— 那不仅多余，还可能与 Sa-Token 的序列化策略冲突。

### 4. 版本核查方法（可复用的经验）

**不要凭记忆猜版本号。** 正确做法是抓 Maven Central 元数据 + 读 starter 的 pom：

```powershell
# 看某个 artifact 有哪些版本
Invoke-WebRequest https://repo1.maven.org/maven2/<group路径>/<artifact>/maven-metadata.xml
```

判断兼容性要看**它内部导入了哪个 BOM**。例如逐个读 MyBatis-Plus 各版本的 starter pom：

| MyBatis-Plus | 内部导入的 spring-boot-dependencies |
|---|---|
| 3.5.9 | 3.3.4 |
| 3.5.12 | 3.4.1 |
| 3.5.13 / 3.5.14 / 3.5.15 | 3.4.1 |
| **3.5.16** | **3.5.9** ← 唯一显式对齐 Boot 3.5 的版本 |

## 二、运行期才暴露的坑

### 5. Logback 用了 `%clr` / `%wEx` 却未注册转换器 → 应用直接启动失败

**现象**：

```
ERROR in ch.qos.logback.core.pattern.parser.Compiler
  - There is no conversion class registered for composite conversion word [clr]
  - [wEx] is not a valid conversion word
IllegalStateException: Logback configuration error detected
```

**根因**：`%clr`（彩色输出）与 `%wEx`（异常堆栈白空格折叠）是 **Spring Boot 对 Logback 的扩展**，
原生 Logback 不认识。自定义 `logback-spring.xml` 时如果用了它们，
必须 include Spring Boot 的默认配置来注册转换器。

**解决**：

```xml
<include resource="org/springframework/boot/logging/logback/defaults.xml"/>
```

**这条最能说明"只编译不启动"的危害** —— 编译 100% 通过，
但应用根本起不来。

### 6. Redis 密码配置成空串，导致 `AUTH` 失败

**现象**：

```
RedisConnectionException: Unable to connect to Redis server: localhost/127.0.0.1:6379
Caused by: RedisException: ERR invalid password. command: (AUTH)
```

**根因**：配置写成了 `password: ${REDIS_PASSWORD:}`。当环境变量不存在时，
Spring 会把它解析成**空字符串** `""` 而不是 `null`。
Redisson 拿到非 null 的密码就会发 `AUTH ""`，Redis 直接拒绝。

**解决**：填真实密码；若 Redis 确实无密码，必须写成 `password:`（留空即 null），
**不能留成空串**。

### 7. Windows 下运行中的应用锁住 jar，导致 Maven 打包卡死

**现象**：`mvn package` 卡在 repackage 阶段 10 分钟以上无任何输出。
检查发现 `nqx.jar` 时间戳还是旧的 —— 根本没走到打包。

**根因**：**Windows 不允许覆盖被运行中进程打开的文件**。
应用正从 `nqx-web/target/nqx.jar` 运行，`spring-boot:repackage` 需要替换这个文件，
于是被文件系统锁住。Linux 下不会有这个问题（允许替换已打开的文件），
所以这个坑只在 Windows 上出现。

**解决**：**先停应用，再打包**。

```powershell
# 正确顺序
$conn = Get-NetTCPConnection -State Listen -LocalPort 8080
if ($conn) { Stop-Process -Id $conn.OwningProcess -Force; Start-Sleep 4 }
mvn clean package -DskipTests
java -jar nqx-web/target/nqx.jar
```

这个坑在 IDE 里 Ctrl+F5 时也会遇到（IDE 帮你停旧进程所以感觉不到），
但用脚本一键部署时必踩。

## 三、数据正确性的坑（代码看起来对，但数据是错的）

### 8. MyBatis-Plus 只给表名加反引号，不给列名加

**现象**：`INSERT INTO sys_operation_log (... operation ...)` 语法错误。

**根因**：MyBatis-Plus 会自动给 `@TableName` 的值加反引号，
但**自动推导出的列名不会加**。而 `operation`、`options`、`user_answer`
这些列名在 MySQL 中有保留字风险。

**解决**：实体上显式转义：

```java
@TableField("`operation`")
private String operation;
```

### 9. 操作人类型约定在两张表里相反

**现象**：同一个管理员，在 `sys_operation_log` 里 `user_type = 2`，
在 `sys_login_log` 里却是 `user_type = 1`。

**根因**：V1 建表时列注释写岔了：
- `order_flow.operator_type` 注释是「1用户 2管理员 3系统」
- `sys_operation_log.user_type` / `sys_login_log.user_type` 注释是「1管理员 2小程序用户」

而 Java 侧 `CommonConstants` 统一用前者。加上 `writeLoginLog` 里还**硬编码了 `1`**，
三处不一致。

**解决**：统一为「**1 小程序用户 / 2 管理员 / 3 系统**」，
新增 `V4__unify_operator_type_comment.sql` 迁移修正列注释并回填错误数据，
代码改为引用常量而非硬编码。

**教训**：同一语义的枚举值，全项目只能有一处定义。
一旦出现两个"看起来都对"的数字，迟早会错。

### 10. 登录与注销的操作人采集时序相反

**现象**：`@Log` 记录管理员登录，`user_name` 却是 `anon`。

**根因**：日志切面在 `point.proceed()` **之前**采集身份，
而登录接口执行前会话还没建立。反过来，注销接口如果在执行后采集，
会话已销毁同样只能拿到 `anon`。

**解决**：执行前后各采集一次，执行后拿得到就用执行后，否则回退到执行前
（详见 [docs/05 §1.4](05-核心组件设计说明.md)）。

**这个坑的价值**：它说明"在方法前后采集数据"这个看似随意的选择，
对于生命周期本身就发生变化的接口（登录/注销）会产生完全不同的结果。
**写 AOP 时必须想清楚：我要观察的是动作发生前还是发生后的状态？**

### 11. MyBatis-Plus 的 NOT_NULL 更新策略导致字段无法清空

**现象**：把商品的所有轮播图删掉后保存，重新查询发现旧图片还在。

**根因**：MyBatis-Plus 默认的更新策略是 `NOT_NULL` —— **null 字段会被直接从 UPDATE 语句中跳过**。
于是 `product.setImages(null)` 这个"清空"操作根本没有生成 SQL。

**解决**：清空时写入空数组字符串 `"[]"` 而不是 `null`：

```java
product.setImages(dto.getImages() == null || dto.getImages().isEmpty()
        ? "[]"                                  // 显式表达"清空"
        : JSONUtil.toJsonStr(dto.getImages()));
```

**推广**：任何需要"把字段改回空值"的场景都会遇到这个坑
（清空备注、清空图标、置空外键）。要么写 `"[]"` 这类哨兵值，
要么用 `UpdateWrapper.set(column, null)` 显式指定。

### 12. 手写 SQL 必须自己带 `deleted = 0`

**现象**：后台已删除的商品仍出现在列表里。

**根因**：MyBatis-Plus 的逻辑删除（`@TableLogic`）**只对它自动生成的 SQL 生效**，
手写 XML 里它完全不介入。

**解决**：所有手写 SQL 显式加上 `deleted = 0`。
本项目在 `ProductMapper.xml`、`SysPermissionMapper.xml` 等文件顶部都有醒目注释提醒。

### 13. LEFT JOIN 的过滤条件写在 ON 还是 WHERE

```sql
-- ✗ 错误：分类被删除的商品会从列表中凭空消失
LEFT JOIN product_category c ON c.id = p.category_id
WHERE p.deleted = 0 AND c.deleted = 0

-- ✓ 正确：只影响能否取到分类名，商品本身仍在列表中
LEFT JOIN product_category c ON c.id = p.category_id AND c.deleted = 0
WHERE p.deleted = 0
```

**原因**：`WHERE` 是对 JOIN 结果集的过滤，作用在 LEFT JOIN 上会把它退化成 INNER JOIN。
列表页宁可显示"分类已删除"，也不能让商品查不到。

### 14. 分页排序不稳定

**现象**：翻页时第 2 页重复出现第 1 页的某条数据，另一条怎么都翻不到。

**根因**：`ORDER BY sort ASC` 中 `sort` 有大量重复值，
MySQL 对相同排序键的行不保证稳定顺序，每次查询返回的次序可能不同。

**解决**：加上唯一列作为最终排序键 → `ORDER BY p.sort ASC, p.id DESC`。

## 四、Flyway 迁移实践

本项目已执行 4 条迁移，正好演示了迁移的正确使用方式：

| 版本 | 内容 | 演示了什么 |
|---|---|---|
| V1 | 21 张表 + 索引 | 初始建表 |
| V2 | 角色/权限树/演示数据 | 初始化数据 |
| V3 | 操作日志加 `trace_id` 列 | **加字段的标准做法**：已执行的 V1 不可修改（校验和会失败），必须新增迁移 |
| V4 | 统一操作人类型列注释 + 回填数据 | **改注释与修数据也走迁移**，保证每套环境执行同一串脚本 |

**关键规则**：
- 迁移脚本一旦执行过就**不允许再修改**（`validate-on-migrate: true` 会校验和并让启动失败）；
- 数据回填类迁移必须先想清楚数据现状再写。
  例如 V4 里的 `UPDATE sys_login_log SET user_type = 2 WHERE user_type = 1` 之所以能无条件执行，
  是因为小程序端尚未实现、表里只有管理员记录。
  **若已存在真实的小程序用户登录记录，这样回填会直接改错数据。**

## 五、排查方法论小结

从这 14 条里能提炼出几条通用经验：

1. **"编译通过"不等于"能跑"**。第 1、2、5、6 条全都是编译期毫无提示、
   运行期直接致命的。**任何依赖升级后都必须真正启动一次。**
2. **不要相信"看起来接上了"**。第 3 条空 jar 如果只看依赖树，
   `sa-token-redis-jackson` 明明在依赖列表里，但功能是缺失的。
   **验证要落到"打开 jar 看里面有没有类"这个粒度。**
3. **数据正确性问题比崩溃更难发现**。第 9、10、11 条都不会报错，
   只会让数据慢慢变脏。**写完功能后一定要查一次数据库里的真实数据**，
   而不是看接口返回 `code=200` 就算通过。
4. **平台差异要专门验证**。第 7 条只在 Windows 上出现，
   在 Linux 上开发和部署的人永远遇不到。

## 六、前后端对接阶段暴露的坑

前面几节大多是在"自己写、自己测"的阶段撞到的。下面这批则不同：
**只有在两份独立实现真正对接时才暴露** —— 它们要么编译期毫无提示，
要么在后端自测时完全正常。这也是本项目坚持每一轮都真实启动、真实调接口，
并在前后端之间安排一次交叉验收的原因。

### 15. Lombok 漏注解：final 字段没有构造器

- **症状**：编译报 `变量 stringRedisTemplate 未在默认构造器中初始化`。
- **原因**：类上写了 `@Component` 却漏了 `@RequiredArgsConstructor`，
  Lombok 不会为 `final` 字段生成构造器，而 Spring 需要构造器注入。
- **教训**：**"final 字段 + 构造器注入"这套写法里，Lombok 注解决定成败。**
  新增 Service/Component 时先确认注解齐备：
  `@Service`（或 `@Component`）、`@RequiredArgsConstructor`、`@Slf4j`。

### 16. 方法写了，但忘了在 Controller 暴露 → 404

- **症状**：`POST /admin/order/{orderNo}/deliver` 返回 `404 接口不存在`，
  但 `AdminOrderService.deliver()` 明明白白写着。
- **原因**：Service 写完了，Controller 里漏加对应的 `@PostMapping`。
- **教训**：**"编译通过"与"接口可用"之间还有一段距离。**
  这类漏接编译期完全不报错，只有真正调一次才会发现。

### 17. 数据库 NOT NULL 与前端契约冲突 → 500

- **症状**：维修申请提交返回 `500 系统繁忙`，日志是 `Column 'contact_name' cannot be null`。
- **原因**：建表时把 `contact_name` / `contact_phone` 定成 `NOT NULL`，
  但旧前端的维修页**只提交 `{order_id, description, images}`**，从不收集联系人。
  于是每次提交都必然违反约束。
- **隐蔽之处**：页面能正常打开、能填描述、能选图，**只有点"提交"那一刻才失败**。
  只测"页面能不能打开"是发现不了的。
- **修法**：V12 迁移把两列改为可空，Service 从 `app_user` 的昵称/手机号兜底填充。
- **为什么不改成"必填校验"**：那要改小程序页面；而用户资料里本来就有昵称和手机号，
  **让用户重复填一遍自己已有的信息是糟糕的设计**。真缺失时客服可在处理环节补录，
  不该因为"某一列没值"就把整笔申请挡在门外。

### 18. lambda 捕获了被重新赋值的局部变量

- **症状**：`lambda 表达式引用的本地变量必须是最终变量或实际上的最终变量`。
- **原因**：一段代码里既对 `productId` 做条件赋值，又用 `stream().filter(i -> ...productId...)`
  捕获它。Java 要求 lambda 捕获的局部变量必须是 effectively final。
- **修法**：先把"要按哪个 ID 查"定进一个 `final` 局部变量，再回填给外层变量。
- **教训**：**"既有条件赋值、又有 stream 操作"的代码段是这类错误的温床。**

### 19. PowerShell 脚本文件必须带 BOM

- **症状**：`scripts/check-permissions.ps1` 执行报
  `表达式或语句中包含意外的标记"鏁版嵁搴撲腑鐨勬潈闄愮爜锛?"` —— 报错里的乱码就是线索。
- **原因**：脚本存成了**无 BOM 的 UTF-8**，而 Windows PowerShell 5.1
  对 `.ps1` 文件默认按 ANSI（GBK）解析，中文注释被解码坏，
  连注释里的字符都可能被当成代码，直接把语法结构冲垮。
- **修法**：写回带 BOM 的 UTF-8：

  ```powershell
  $text = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
  [System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($true)))
  ```

  验证：文件前 3 字节应为 `239,187,191`。
- **注意区分**：这**只针对 `.ps1`**。
  Java 源码、YAML、SQL、Markdown 都**不应该**加 BOM ——
  Java 源码带 BOM 会导致编译报错，SQL 带 BOM 可能让第一条语句解析失败。
  **"需不需要 BOM"取决于解析器的宽容度，不能一刀切。**

### 20. YAML 里写了 C 风格注释

- **症状**：`docker compose config` 报 `project name must not be empty`（实际是解析失败）。
- **原因**：在 `docker-compose.yml` 里顺手写了 `/* ... */`。
  **YAML 只认 `#`**，`/*` 会被当成非法键名，整份文件解析失败。
- **教训**：跨文件写注释最容易串语法。**改完配置类文件务必跑一次解析校验**
  （`docker compose config`、`nginx -t`、`promtool check config` 都是这类工具）。

### 21. 注释块没闭合

- **症状**：编译报 `未结束的注释`。
- **原因**：用 `/*` 开了注释块，写完后忘了 `*/`。
- **教训**：这类手误靠"仔细"防不住，**靠"每次编辑后编译一次"防得住**。

### 22. 分页体与裸数组的契约不一致（影响面最广）

- **症状**：列表页 `.map is not a function`，整页白屏。**至少 7 个列表页受影响。**
- **原因**：
  - 旧后端列表接口返回 `res.json({ data: rows })`，`rows` 是**数组**；
  - 新后端统一返回 `PageResult{records, total, current, size, pages}`；
  - 经兼容层外层 `data` 包装后，页面拿到 `{ data: { records: [...] } }`，
    **`res.data.data` 是对象而不是数组**。
- **修法**：兼容层加一步 `unwrapPagePayload` —— payload 若是分页体就解出 `records`。
  **一处修复、7 个页面全部生效。**
- **为什么不在页面里改**：要动 7 个页面的十几处取值，以后每加一个列表接口还要记得改。
  **适配层的价值就在于把差异收敛到一个地方。**
- **代价要讲清楚**：页面因此拿不到 `total`，无法做服务端分页。
  但旧后端本来就没返回 total，旧页面也从未做过服务端分页 ——
  **这不是能力退化，是精确还原了旧契约。**

### 23. 权限码拼错：编译、启动都不报错，只有调用时 403

- **症状**：后台题库检索返回空值，实为 `403 缺少权限：question:list:list`。
- **原因**：数据库里的权限码是 `question:list`，Controller 注解写成了 `question:list:list`。
- **隐蔽之处**：`@SaCheckPermission("xxx")` 是**字符串字面量**，
  与数据库权限码之间没有任何编译期约束。对不上时编译通过、启动通过，
  只有真正调那个接口才 403；而 403 又容易被误认为"登录态过期"或"角色没配好"。
- **修法**：写了 `scripts/check-permissions.ps1`，把所有 Controller 用到的权限码
  与数据库权限表交叉比对。**全量跑一次只发现这一处不一致**，几秒钟定位。
- **推广**：凡是"代码里的字符串键"需要与"数据源里的键"对齐的地方
  （权限码、Redis Key 前缀、配置项名），都值得写一个这样的校验脚本。

### 24. 假成功：没有 fail 回调的"操作类"请求

旧函数 `simulateSettle`、`handleRemindShip` 调用的接口已被安全下线，
但**它们没有 `fail` 回调**：兼容层 reject 之后，页面**仍然弹「结算成功」「已提醒」**。

```js
wx.cloud.callContainer({
  path: '/api/procurement/orders/ship',
  success: () => wx.showToast({ title: '已提醒', icon: 'success' })
  // ← 没有 fail，请求失败时什么都不会发生，用户却以为成功了
});
```

**假成功比报错危险得多**：报错至少会有人去看，假成功会让用户以为业务已完成，
等到对不上账才发现。修法是如实说明真实流程（发货与结算都是管理端动作），
**不再声称完成了任何操作**。

由此得到一条规则：**任何"操作类"请求都必须处理失败分支**，
哪怕只是 `wx.showToast({ title: '操作失败', icon: 'none' })`。

### 25. "注释比实现更乐观"

`biz_order.version` 在早期注释里被描述成"用于乐观锁，版本不匹配会更新 0 行"。
但实体上**没有 `@Version` 注解**，MyBatis-Plus 不会生成 `WHERE version = ?` ——
它实际只是个"变更次数计数器"。

- **为什么最终没启用真乐观锁**：
  1. 状态机已挡住绝大多数并发非法流转（第二次请求因状态不合法被拒）；
  2. 真正的重复结算由 `points_record` 的唯一索引兜底，这是更可靠的防线；
  3. 启用 `@Version` 后**所有 `updateById` 都必须传旧版本号**，
     漏传会导致 `WHERE version = null` 匹配不到行、更新**静默失败** ——
     这是个很容易埋雷的约束，收益不抵风险。
- **教训**：**注释里写"实现了 X"之前，先确认 X 真的生效了。**
  一段不准确的注释比没有注释更坏，它会让人在排查时排除掉正确的方向。

### 26. 同一个字段名，两端期望的形状不同

- **症状**：采购订单页的商品列表、收货人、金额，以及**所有操作按钮**都不显示。
  页面不报错，只是"什么都没有"。
- **原因**：旧库把两类订单拆成了 `orders` 与 `procurement_orders` 两张表，
  它们各自演化出了不同的字段形状与状态词表，而**新接口只按其中一套实现**：

  | 页面读取 | 最初下发的 | 结果 |
  |---|---|---|
  | `order.products`（明细数组） | 未提供 | 商品列表空白 |
  | `order.address.name/.phone/.address`（嵌套对象） | 扁平字符串 | 收货人空白 |
  | `order.total_amount`（元） | 未提供 | 合计 ¥ 空白 |
  | `prod.count`（数量） | 字段名是 `quantity` | 数量空白 |
  | 状态 `pending_payment`/`pending_shipment`/`pending_receipt` | `pending`/`processing` | **所有按钮都不显示** |

- **最危险的一条是状态词表**：采购订单页写的是
  `wx:if="{{item.status === 'pending_payment'}}"`，
  状态值对不上时按钮**永远不渲染**。页面看起来正常、控制台没有报错、
  接口返回 `code=200` —— 只是"没有按钮可点"。
  **这类问题比报错难查一个数量级**，因为没有任何一处会提示你哪里不对。
- **修法**：按订单类型分流状态词表（回收单一套、采购单一套），
  并把 `products` / 嵌套 `address` / `total_amount` 补齐。
- **关于 `address` 的取舍**：回收单页面读的是扁平字符串 `{{order.address}}`，
  采购单读的是嵌套对象。三个方案里选了「统一成对象 + 改回收页一行模板」：
  按类型返回不同形状虽然能让页面一行不改，但**同一个字段的类型随数据变化**
  是接口设计里应当极力避免的形态 —— 调用方没法写类型，排查时也无法从字段名推断内容。

### 27. 「不报错的空白」是兼容层最难发现的一类问题

第 26 条的共同特征是：**页面不报错、接口返回 200、数据就是不出来。**

这与第 24 条的"假成功"是同一类问题的两面：
- 假成功：操作没生效，却提示成功；
- 空 白：数据没下发，却不报错。

两者都无法靠"看日志"发现，只能靠**逐字段核对页面模板里到底读了什么**。
所以本次采用了机械做法：把页面里所有 `{{ }}` 与 `path:` 都提取出来，
逐一对照接口返回的字段名，而不是凭记忆判断"应该够了"。

> **一条可复用的做法**：接口兼容性检查不要靠读代码，要**从消费方反查**。
> 把前端模板里出现的字段名全部列出来，与后端 VO 的字段名做**集合差集** ——
> 差集就是会显示空白的地方。
>
> 同理，`scripts/check-permissions.ps1` 做的是"权限码"的集合差集。
> 二者是同一种方法：**凡是"字符串键需要在两处对齐"的场景，都用差集来找问题。**

### 28. 路径前缀只配了一半：采购端的地址列表永远是空的

**现象**：小程序里保存地址成功（数据库确实有 4 条），但地址列表页始终显示
「暂无收货地址」。接口用 curl 打是 `200` + 4 条数据，页面读 `res.data.data`
却拿到 `undefined`。

**根因**：旧后端的两类客户端用了**不同的路径前缀** ——

```
回收端：/api/address/list
采购端：/api/procurement/address/list
```

而垫片里「需要还原外层 `data`」的配置只写了 `/api/address/` 这一条前缀。
用户的角色是 `procurement`，走的是采购端路径 —— **恰好是没配的那一端**。
于是响应没有被包装，页面读 `res.data.data` 得到 `undefined`，
`addressList.length` 是 `undefined`，`wx:if` 判定为假 → 显示空状态。

**为什么特别难查**：

- 请求成功、状态码 200、数据库里也确有数据 —— 三个"正常"的信号同时成立；
- 页面不报错，只是"没有数据"，与"真的没有数据"外观完全一致；
- 我前两次排查都被误导了：用 curl 验证只能证明**后端**对，
  证明不了**页面**能读到；用 `grep` 查配置时，`'/api/address/'`
  这个**子串**能匹配到 `'/api/address/list'`，我因此误判成"已配置"。

**修法**：补上 `/api/procurement/address/` 与 `/api/procurement/orders/` 两条前缀，
并把它们的子路径里"不返回外层 data"的那些（`create`/`pay`/`cancel`/`receive`）
逐个加进例外表。

> **两条可复用的教训**：
> 1. **同一个业务两端各有一套前缀时，配置必须成对写。** 只配一端，
>    出问题的恰恰是没配的那一端，而且不报错。
> 2. **验证方法本身也会错。** `grep` 子串匹配、`curl` 打接口都属于
>    "间接证据"，它们能排除问题，但不能证明问题不存在。
>    最终是靠 `scripts/audit-shim-wrapping.js` 把**页面用到的所有路径**
>    与**配置表**做集合差集才定位到的 —— 这是第 27 条那个方法论的又一次应用。

### 29. `session.set(key, null)` 在 ConcurrentHashMap 上必然抛 NPE

**现象**：管理后台「系统管理」模块接上权限缓存刷新后，
`POST /admin/system/permission` 直接 500。

```
java.lang.NullPointerException
    at java.util.concurrent.ConcurrentHashMap.putVal
    at cn.dev33.satoken.session.SaSession.set
    at com.nqx.service.system.StpInterfaceImpl.evictCache
```

**根因**：写缓存失效时用的是

```java
session.set(SESSION_KEY_ROLES, null);   // ← 这里
```

而 Sa-Token 的 Account-Session 底层是 `ConcurrentHashMap`，
**`ConcurrentHashMap.put(key, null)` 会直接抛 NPE**（它不允许 null 值）。
也就是说这个方法只要被调用就必然 500，与缓存逻辑本身无关。

**它为什么潜伏了这么久**：在此之前**没有任何地方调用它**（死代码）。
直到真正需要"改了权限就刷缓存"时接上，才第一暴露。

**更值得记的是我当初的取舍**。原注释写的是：

> 这里把缓存值置为 `null` 而不是删除 key……这样避免依赖
> SaSession 是否提供 `delete` 方法，语义上也足够清晰。

**这个理由是错的，而且是"猜"出来的**：我当时没去确认 SaSession 有没有
`delete`，就假设它可能没有，然后绕开 —— 绕进了一个必炸的分支。
实际上 `delete` 一直存在（`ConcurrentHashMap.remove` 对不存在的键也安全）。

> **教训**：**「避免依赖某个 API」这种理由，只有在确认过替代方案可行时才成立。**
> 拿不准的 API，花十秒看一眼文档或方法签名，比写一段听起来合理的注释更划算 ——
> 因为**注释不会被编译器检查**，而它会误导后来的人（包括几个月后的自己）。

### 30. 「逻辑删除 + 唯一索引」的冲突：能用表结构解决的事，别让业务代码迁就

**现象**：管理后台同名的管理员账号**第二次**被删除时必然 500。

```
ERROR 1062: Duplicate entry 'dup_test-1' for key 'sys_user.uk_username'
```

**根因**：唯一索引是 `uk_username(username, deleted)`，而逻辑删除只是把
`deleted` 从 0 改成 1。于是同一个账号被删两次后，库里出现两行
`(username, 1)` → 撞唯一键。也就是说这条完全正常的运维路径必然失败：

```
创建账号 A → 删除 A → 再创建同名 A → 再删除 A    ← 这里 500
```

**三次尝试，前两次都不对**：

| 方案 | 结果 |
|---|---|
| ① 函数索引 `(username, (IF(deleted=0, 0, id)))` | ❌ MySQL 拒绝：<br>`ERROR 3754: Functional index cannot refer to an auto-increment column` |
| ② 业务层"退避"：删除前把用户名改成 `原名#del#<id>` | 🟡 能跑通，但**把 username 这个审计字段改坏了** |
| ③ 把 `deleted` 放宽为 BIGINT，删除时写入**本行 id** | ✅ 正解 |

**方案 ② 的实际代价**（实测数据）：

```
id=2   sys_tester          ← 原始
id=4   sys_tester#del#4    ← 第 2 次删除时被迫改名
id=9   sys_tester#del#9
```

事后根本看不出"这个被删的账号原来叫什么"，而且用户名会随着删除次数
不断堆积后缀。**它绕开了撞键，但毁掉了审计线索。**

**方案 ③ 的原理**：让唯一索引的第二部分语义变成

- 未删除的行：`deleted = 0` → 同一 username 全局唯一（原始需求成立）
- 已删除的行：`deleted = 本行 id` → 每行都不同，同一 username 可无限次删除

且**用户名保持原样**。同时 BIGINT 完全兼容原有的 0/1 语义，
MyBatis-Plus 的逻辑删除过滤 `WHERE deleted = 0` 不受影响。

**迁移脚本自己还踩了一个坑**：第一版把语句顺序写反了 ——
先"还原被改坏的用户名"、后"写 deleted = id"，结果迁移自己在
还原那一步就撞了唯一键：

```
SQL State  : 23000
Error Code : 1062
Script V13__fix_logical_delete_unique_key.sql failed
```

因为那一刻库里同时存在 `(sys_tester, deleted=1)` 与
`(sys_tester#del#4, deleted=1)`，把后者改回 `sys_tester` 立刻冲突。
**语句本身都是对的，错的只是它们之间的先后关系。**

> **三条教训**：
> 1. **能用表结构解决的事，不该让业务代码去迁就。** 业务层的"退避"
>    看起来只是多几行代码，实际是把一个数据模型缺陷转化成了**数据本身的损坏**。
> 2. **数据修复脚本的顺序必须写清楚。** 每句 UPDATE 单独看都对，
>    顺序错了整个脚本就失败 —— 而且失败发生在"你没想到会冲突"的那一句。
> 3. **MySQL 的 DDL 不参与事务**。第一次失败时 `ALTER TABLE` 其实已经生效了
>    （`deleted` 确实变成了 bigint），所以修完顺序还必须让脚本**能重复执行**
>    （`MODIFY COLUMN` 改成同样类型是幂等的），否则"改对了也跑不起来"。
>    同时别忘了清掉 Flyway 里 `success = 0` 的失败记录。

### 31. 把"清空全部数据"的脚本当成"清缓存"随手执行，删掉了用户的真实历史

**现象**：用户反馈「我登录了，里面的历史记录肯定不能消失啊，正常软件肯定会保留」。

**第一步先查设计有没有问题** —— 这一步很重要：用户的描述往往指向某个设计缺陷，
但不能假定他说的一定是代码 bug。实测结论：

```
第1次登录  userId=15  → 新增地址 ✅ → 提交回收单 ✅ RC20261019135044892133
第2次登录  userId=15  身份一致 ✅   历史订单数=1  历史地址数=1   ← 全部保留
第3次登录（换一个全新 code）userId=15 同一用户 ✅   历史订单数=1
```

**登录与历史保留的逻辑是正确且稳定的**：
`AppAuthService.login` 按 openid 查用户，存在就复用（`status: existing_user`），
不存在才创建。mock 模式下 openid 由固定种子映射，所以换 code 也命中同一个用户。

**真正的原因在工具上**：项目里有一个 `scripts/reset-business-data.sql`，
它的第一条数据操作就是 `DELETE FROM app_user` —— **删用户账号**。
账号一删，名下订单、地址、积分流水的归属全部断裂，且**没有任何备份**。

而我在收尾"把数据恢复成干净状态"时，把它当成"清一下测试数据"**直接跑了**，
前后跑了好几次。用户的真实使用记录就是这样一次次被抹掉的。

**为什么这个错误特别典型**：

- 脚本名叫 `reset-business-data`，「重置业务数据」听起来像"清缓存"级别的操作，
  **名字没有传达出它会删账号**；
- 它还会打印一段漂亮的自检报告（「业务数据全为 0」），
  看起来像"按预期完成"，**给出正反馈**；
- 每次都"成功"，所以没有任何一次会触发警惕。

**修法（三层防护）**：

1. **强制口令**。脚本里加了 `SIGNAL SQLSTATE '45000'` 守卫：
   没有 `SET @nqx_confirm_wipe := 'WIPE-ALL-DEMO-DATA';` 这行确认，
   脚本**一条数据都不删**就直接报错退出。口令故意放在需要手动取消注释的位置，
   逼操作者先读一遍说明。

   ```
   ERROR 1644 (45000): 已拒绝执行：本脚本会删除全部用户账号与其历史记录（不可恢复）。
   ```

2. **备份先行**。新增 `scripts/backup-database.ps1`：导出后用文件大小、
   `Dump completed` 标记、关键表建表语句三重校验，并打印恢复命令。
   **并且真的做过一次恢复演练**（还原到临时库，行数与原库一致后才删掉临时库）。

   > 写这个脚本时又踩了一个 PowerShell 的坑：`$ErrorActionPreference='Stop'`
   > 下，mysqldump 往 stderr 写的「password ... can be insecure」会被当成
   > 致命错误终止脚本 —— 第一次用 `2>&1` 失败，第二次以为改成 `2>` 重定向就没事，
   > **其实一样会终止**。根源不是重定向符，而是 `ErrorActionPreference`。
   > 正确写法是临时降级再恢复，只看退出码。

3. **文档改口径**。运维手册里把「数据重置」从"日常操作"改成"⚠️ 危险操作"，
   并强调：**只想清掉自己测试的几行，就按 id/昵称精确删，不要用这个脚本。**

> **三条教训**：
> 1. **「清空全部」和「清理我造的」是两种操作，绝不能用同一个脚本。**
>    前者需要备份与口令，后者只需要精确的 WHERE 条件。
> 2. **危险脚本的命名要说出后果，而不是说出意图。**
>    `reset-business-data` 听起来无害；如果叫 `delete-all-users-and-orders`，
>    我大概会先愣一下。**名字是最后一道人机防线。**
> 3. **成功输出会麻痹人。** 脚本每次"成功"都在强化"我在做正确的事"的错觉。
>    对破坏性操作，应该在**执行前**要求显式确认，而不是在执行后打印漂亮的报告。

### 32. 联调测试造的权限节点留在了生产配置里，后台菜单出现 4 个「临时子目录」

**现象**：管理后台的侧边栏里，除了正常的业务菜单，还多出 **4 个「临时子目录」**和
**4 个「联调测试菜单」**。超级管理员的权限列表里也有它们。

**根因**：开发系统管理模块时，为了验证「新增权限节点 / 移动节点 / 删除节点」这几个接口，
反复建了一批 `test:` 前缀的节点。接口测通了，但**测完没有清理**：

```
id 6014  perm_name=联调测试菜单(已改)  perm_code=test:menu:list     path=/product/test
id 6016  同上
id 6018  同上
id 6020  同上
id 6015  perm_name=临时子目录         perm_code=test:subdir:list   path=/system/tmp
id 6017  同上
id 6019  同上
id 6021  同上
```

这 8 个节点是**真实存在于权限表里的配置数据**，所以菜单渲染、权限校验都会认它们。

**为什么特别隐蔽**：联调时你正在测"新增权限"，所以看到多出来的菜单会觉得
"嗯，刚建的那个生效了"—— **测试成功本身就是污染的证据，但它看起来像功能正常的证明。**

**修法（V14 迁移）**：

1. 按 `perm_code LIKE 'test:%'` 删除这 8 个节点及其角色关联。
   **用前缀而不是 id 列表**，是为了把可能漏掉的同类节点也一并清掉；
   `test:` 是联调测试的约定前缀，正式权限码形如 `sys:user:list`、`order:recycle:audit`。
2. 顺手补上了缺失的「用户管理」菜单（见下一条）。

> **三条教训**：
> 1. **测试数据必须有可识别的标记，并且测完立刻删。** `test:` 前缀这部分做得对，
>    错的是"没删"。没有标记的测试数据（比如随便起的 `abc`）根本没法批量清理。
> 2. **凡是"新增"类接口的联调，都要在测完后回查一次"现在表里有什么"。**
>    验证"加成功了"和验证"只剩下该加的"是两件事。
> 3. **生产配置表不该承受联调压力。** 更彻底的做法是联调用独立的测试库/测试租户，
>    而不是在真实配置表上反复增删。

### 33. 用 SQL 直接改权限，后台仍然 403 —— 因为权限码缓存在 Account-Session 里

**现象**：新增了「用户管理」菜单并给超级管理员授权（直接插 `sys_role_permission`），
数据库确认有这个权限，但后台访问 `/admin/app-user/page` 仍然返回：

```
{"code":403,"msg":"缺少权限：app:user:list"}
```

**根因**：`StpInterfaceImpl` 把管理员的权限码缓存进 Sa-Token 的 **Account-Session**：

```java
Object cached = session.get(SESSION_KEY_PERMISSIONS);
if (cached instanceof List) { return (List<String>) cached; }   // 命中就不查库
```

这个缓存的两个特点决定了问题：

- **按登录用户 id 缓存**（`getSessionByLoginId`），不是按 token —— 所以换一个 token 也一样命中；
- **持久化在 Redis**，所以重启应用也不会清掉。

而"改权限就刷缓存"的逻辑（`AdminPermissionCacheEvictor`）只在**走 Service 的接口**里被调用。
直接执行 SQL / 迁移脚本改 `sys_role_permission`，没有任何代码知道这件事，
缓存自然还是旧的。

**修法**：删掉那个管理员的 Account-Session：

```bash
redis-cli -a <密码> DEL 'Authorization:admin:session:<管理员id>'
```

**注意不要用 `FLUSHDB`** —— 那会把所有小程序用户的登录态一起清掉，
而实际只需要让受影响的那一个管理员重新加载权限。

> **三条教训**：
> 1. **"改了数据库"和"系统知道改了"是两件事。** 凡是有缓存的地方，
>    直接改库都等于"绕过系统改状态"，必须知道对应的失效手段。
> 2. **缓存键的设计要能定位到单个用户。** 这里按 `loginId` 缓存，
>    所以能精确删一个会话；如果缓存的是"全量权限表"，就只能整体重建。
>    **按最小粒度分键，运维时才有精细操作的空间。**
> 3. **用 SQL 改权限是紧急手段，不是常规手段。** 常规途径是走管理后台的
>    「角色管理 → 分配权限」，那条路径会自动刷缓存。

### 34. 四处把微信「临时文件路径」写进了数据库，图片第二天全部失效

**现象**：用户当天换的头像、发的评价晒图、传的维修凭证，**第二天全部打不开**。
接口一直返回 200，页面也不报错，只是图片变成空白/裂图。

**根因**：`wx.chooseAvatar` 和 `wx.chooseImage` 返回的都是**临时文件路径**
（`wxfile://tmp_xxx` 或 `http://tmp/xxx.jpeg`）。它有两个致命性质：

- 只存在于当前微信客户端会话，**重启小程序或换设备就失效**；
- 指向手机本地文件，**服务端根本读不到**。

代码里有 4 处直接把它存了起来，而且旁边都留着一句"注释式许愿"：

```js
// pages/profile/edit/index.js
// 微信返回的 avatarUrl 是临时路径，需要上传到服务器
// 这里为了演示，我们假设上传成功并直接使用临时路径   ← 然后真的存了

// pages/procurement/orders/review/index.js
// In real app, upload here. For now, use temp path.   ← 然后真的提交了

// pages/procurement/repair/apply/index.js
// In a real app, upload these files to server here    ← 然后真的提交了

// pages/login/index.js
this.setData({ tempAvatarUrl: avatarUrl });   ← 收了，然后什么也没做
```

**为什么这个问题特别难被发现**：

1. **当天是好的。** 临时路径在本次会话内完全有效，所以自测时怎么试都正常；
2. **失败是静默的。** 没有异常、没有错误码，只是图片渲染不出来；
3. **注释看起来像"已经考虑过了"。** 那句 "need to upload" 反而让人以为作者知道这件事，
   只是"暂时用演示方案"——而没有任何地方标记这个"暂时"何时该结束。

**修法**：

1. 新增 `POST /app/file/upload`（需要登录，防止匿名写文件），返回**相对路径**
   `/files/avatar/2026/10/19/xxx.png`；
2. 新增 `utils/upload.js`，把「上传 + 解析响应 + 补全绝对地址」收敛成一份实现，
   4 个页面共用；
3. **区分显示与存储两种形态**：
   - 数据库存**相对路径**（写死域名后换机器、换端口、上云托管，图片就全挂）；
   - `<image src>` 用**绝对地址**（小程序会把 `/files/...` 当包内路径去找，结果是空白）。
4. 登录页的「完善资料」：登录成功后才上传头像（此时才有 token），
   再把昵称+头像一起写回；**失败不阻塞登录** —— 资料没保存不该让人登不进去。

> **四条教训**：
> 1. **"演示方案"必须有一个明确的结束条件。** 代码里写 "for now"、"为了演示"，
>    等于给未来埋了一个没有到期日的 TODO。要么当时就做对，要么留 `// TODO(截止日期)`。
> 2. **`wx.chooseImage` / `wx.chooseAvatar` 返回的永远不是可持久化的地址。**
>    这是微信 API 的固定行为，不是偶发问题 —— 见到这两个 API 就该想到上传。
> 3. **静默失败要主动消灭。** 图片加载不出来不报错，所以必须靠"地址形态是否正确"
>    在代码层面保证，而不是靠自测。
> 4. **`wx.uploadFile` 的 `res.data` 是字符串，不是对象。** 直接当对象用会得到
>    `undefined`，同样完全静默。这是它与 `wx.request` 最大的行为差异。

### 35. 导出功能里，错误响应被当成了文件存下来，用户得到「文件已损坏」

**现象**：点「导出」，浏览器下载下来一个 `.xlsx`，用 Excel 打开提示**"文件已损坏"**。
换成另一个有数据的筛选条件，导出又正常了。

**根因**：前端用 `responseType: 'blob'` 取文件。但**失败时**后端返回的是

```json
{"code":400,"msg":"当前筛选条件下没有数据可导出","success":false}
```

—— 它同样会被 axios 包成一个 Blob。如果代码不看内容直接存文件，就会得到一个
后缀是 `.xlsx`、内容却是 JSON 的文件。Excel 打开它当然报"已损坏"。

**为什么这是最糟的失败方式**：报错被**伪装成了成功**。用户看到文件下载完成，
不会有任何"操作失败"的感知，直到打开文件才发现不对；而且第一反应通常是
"这个系统的导出功能是坏的"，而不是"我没选到数据"。

**修法**（`utils/download.ts`）：下载前先看 `blob.type`

```ts
if (blob.type.includes('application/json') || blob.type.includes('text/')) {
  const text = await blob.text()
  const body = JSON.parse(text)
  throw new Error(body.msg || '导出失败')   // 把后端提示原样抛给用户
}
```

后端侧也配合做了一件事：**没有数据时明确报错，而不是导出一个只有表头的空文件。**
一个只有表头的 xlsx 很容易被误认为"导出成功但真的没数据"。

**顺带踩到的两个坑**：

- **导出行类放错模块。** 第一版把带 `@ExcelProperty` 的导出行类放进了 `nqx-pojo`，
  编译报"程序包 `cn.idev.excel.annotation` 不存在" —— 因为 `fastexcel` 只被
  `nqx-service` 引入。**当时的诱惑是"给 pojo 补一个依赖就完事了"，但那会让
  纯数据模块背上一个 Excel 库和一串传递依赖。** 正确做法是把类移到
  `nqx-service/.../export/row/` 下：它本来就属于导出这个服务层职责。
- **`fetch`/`axios` 的 blob 一定记得 `revokeObjectURL`。** 每次导出都创建一个
  object URL，不释放就一直留在内存里。

> **两条教训**：
> 1. **凡是"拿二进制"的接口，都要单独处理错误分支。** 成功是文件、失败是 JSON，
>    这两种内容共用同一个响应通道 —— 分不清就会把错误存成文件。
> 2. **"没有数据"要报错，不要产出空文件。** 空文件会被当成"成功但无数据"，
>    而明确报错能立刻把问题定位到"筛选条件"上。

### 36. MyBatis 直接映射 VO 时，那些"算出来的"字段全是 null（接口照样 200）

**现象**：新建的管理端维修工单列表里，「状态」列和「保修判定」列全都显示 **「-」**。
但详情接口返回的同一个单子是正常的。

**根因**：同一个 VO 有两种构建方式，而只有一种会填派生字段。

```java
// 方式一：详情 —— 走 from()，派生字段全填
public static AdminRepairApplyVO from(RepairApply apply) {
    vo.setStatusText(RepairApplyVO.statusText(apply.getStatus()));
    vo.setWarrantyTypeText(warrantyTypeText(apply.getWarrantyType()));
    ...
}

// 方式二：列表 —— 走 Mapper 的 resultType，MyBatis 按列名直接塞值
//         **它不会调用 from()**，所以 statusText / warrantyTypeText / images 全是 null
<select id="selectAdminPage" resultType="com.nqx.pojo.vo.app.AdminRepairApplyVO">
```

**为什么极难发现**：

1. **接口返回 200**，字段也确实"在响应里"（只是值为 null）；
2. **前端有兜底**：`row.statusText || '-'` —— 安静地显示成「-」，看起来像"这个单子没有状态"；
3. **编译通过、页面不报错、没有异常日志**，三个"正常"信号全都在。

我是**实际打印了一次响应体**才发现的：`{"status":1,"warrantyType":"paid", ...}` ——
有 `status` 却没有 `statusText`，一眼就看出不对。

**修法**：在 Service 里补一步

```java
result.getRecords().forEach(AdminRepairApplyVO::fillDerivedFields);
```

**同一个坑的第二个表现**：`images` 列在库里是 **JSON 字符串**
（`["a.jpg","b.jpg"]`），而 VO 的字段是 `List<String>`。MyBatis 不会自动转换，
`r.images AS images` 的结果是 **null** —— 同样静默。所以拆成两个字段：

```
列 images (JSON 字符串) ──映射──▶ imagesRaw (String, @JsonIgnore)
                                      │
                                 Service 解析
                                      ▼
                                  images (List<String>) ──输出给前端
```

> **四条教训**：
> 1. **"字段存在"不等于"字段有值"。** 验证接口时不要只看有没有报错，
>    要**真的看一眼响应体**里的值。
> 2. **一个 VO 有两种构建路径时，派生字段必然只有一条路径会填。**
>    要么两条路径都调用同一个 `fill` 方法（本项目的做法），
>    要么干脆不要在 VO 里放派生字段、让前端自己算。
> 3. **MyBatis 的 `resultType` 只做列到属性的搬运**，不做类型转换、不调用工厂方法。
>    JSON 列 → List、枚举列 → 枚举，这类映射都得自己处理。
> 4. **前端的 `|| '-'` 兜底会把问题藏起来。** 它让"字段是 null"看起来像
>    "业务上就是空"，而这两者的排查方向完全不同。

### 37. 搜索框是「前端假过滤」，只搜当前那一页

**现象**：商城主页的搜索框能用，但搜不到第 2 页的商品。
更怪的是：明明知道某个商品存在，搜它的名字却什么都没有。

**根因**：

```js
onSearch(e) {
  const keyword = e.detail.value;
  // Client-side filtering for mock        ← 注释自己都承认了
  const filtered = this.data.products.filter(p => p.name.includes(keyword));
  this.setData({ products: filtered });
}
```

它**根本没有发请求**，只是在"已经加载出来的那 10 条"里做字符串匹配。
所以：

- 商品在第 2 页 → 搜不到；
- 商品是刚上架的（本地缓存还没刷）→ 搜不到；
- 搜索完再点别的分类，`this.data.products` 已经被过滤过，
  后续逻辑就在一个"残缺的列表"上操作，越用越乱。

而后端 `ProductMapper.xml` 里 `query.name` 的模糊查询**一直是好的**：

```xml
<if test="query.name != null and query.name != ''">
    AND p.name LIKE CONCAT('%', #{query.name}, '%')
</if>
```

能力在，只是没人调用。

**修法**：搜索改成调接口，把关键词作为 `name` 参数传下去；

```js
if (kw) params.push('name=' + encodeURIComponent(kw));
```

同时搜索时**清掉分类筛选** —— 两个条件同时生效很容易得到空结果，
而用户对"搜索"的预期通常是全局的。

**顺带一个坑**：后端参数叫 `name`，不叫 `keyword`。
我第一次用 `keyword=` 测试，接口**忽略了未知参数**、返回全部商品，
看起来像"搜索没生效"。Spring 绑定不认识的查询参数时是**静默忽略**的，
不会报错 —— 所以传错参数名时，表现是"条件没起作用"而不是"报错"。

> **三条教训**：
> 1. **`// for mock` / `// 简化处理` 这类注释是技术债的标记**，不是免责声明。
>    它标记的是"这里有个功能是假的"，应当被当成 TODO 处理掉。
> 2. **凡是有服务端能力却没被调用的地方，都要怀疑是不是前端自己凑合实现了。**
>    搜一下后端有没有对应参数，往往能省掉重写。
> 3. **传错查询参数名不会报错。** 前端写 `keyword=`、后端认 `name=`，
>    接口返回 200 和全部数据 —— 这种"静默降级"只能靠核对接口文档发现。

### 38. 管理后台有个字段能填、数据库也存了，但没有任何地方展示它

**现象**：管理员在「商品分类」里给分类填了「图标地址」，保存成功、
重新打开还在，数据库里也确实有值 —— 但小程序里**任何地方都看不到这个图标**。
使用者第一反应是"是不是假的 / 是不是没保存"。

**根因**：这个字段**没有消费者**。

| 环节 | 状态 |
|---|---|
| `product_category.icon` 列 | ✅ 存在 |
| 后端 `CategoryVO.icon` | ✅ 有，`/admin/product/category/tree` 与 `/app/product-category/list` 都下发 |
| 管理后台编辑表单 | ✅ 能填、能存 |
| **小程序展示** | ❌ **完全没有**（全项目搜 `icon` 都没有分类相关的渲染） |

更要紧的是：小程序**连分类接口都没调过**。采购端首页只有"搜索框 + 商品列表"，
没有任何分类导航。

所以这不是"数据是假的"，而是**功能缺了一半**：给了录入入口，没给展示出口。

**修法**：在采购端首页补上分类导航，让这个字段真正有地方显示。

顺带发现两个相关设计问题：

1. **两级分类不能直接用父级 id 筛商品**。商品挂在**叶子**分类上
   （`product.category_id = 11`「锂锰电池 CR 系列」），
   而图标通常配在**父级**（`id = 1`「纽扣电池」）。
   按父级 `categoryId=1` 查会得到 **0 条**。
   所以导航做成两级：选大类 → 选小类 → 才按小类 id 筛选。

2. **`icons.js` 只有 33 个预置图标**。我第一次写了 `name="layout-grid"`，
   而它不存在 —— 小程序对不存在的组件属性**不报错**，只是渲染成空白，
   结果是"图标位置一片空"。现在加了校验步骤：从 wxml 里抽出所有
   `name="..."`，逐个比对 `icons.js` 的 key。

> **三条教训**：
> 1. **"能填进去"不等于"能用"**。每个录入字段都该能回答
>    "谁读它？在哪显示？"。答不上来的，要么补上消费者，要么从界面撤掉。
> 2. **用户说"是不是假的"时，先别急着辩解 —— 去查有没有消费者。**
>    数据是真的、但功能缺一半，这种状态在用户看来和"假的"没区别。
> 3. **图标名/枚举值这类"字符串外键"必须校验。** 小程序、Vue 组件对拼错的
>    属性名一律静默忽略，只会渲染成空白 —— 没有报错可看。

### 39. 照「类名」猜接口路径，猜错后前端只表现为"少了一块数据"

**现象**：给采购端首页加好分类导航后，页面渲染正常，但分类栏里**只有「全部」**，
两个真实分类（纽扣电池 / 实验耗材）没出来。没有报错、没有 toast，
就是安静地少了两项。

**根因**：我把接口路径写错了。

```java
// 真实的控制器
@RequestMapping("/app/product/category")     // ← 注意是 /product/category
public class AppProductCategoryController {  // ← 类名却是 product-category
    @GetMapping("/list")
```

我在垫片里照着**类名**写成了：

```js
'/api/procurement/categories': { path: '/app/product-category/list', method: 'GET' }
//                                                    ↑ 多了连字符、少了斜杠
```

后端日志给出了确切答案：

```
20:28:42.815 WARN ... GlobalExceptionHandler : 资源不存在 | app/product-category/list
```

是 **404「资源不存在」**，不是 401、也不是空数据。

**为什么难发现**：

1. 前端页面**不报错** —— `res.statusCode` 是 200（统一返回体），
   我只是判了 `statusCode !== 200` 就 `return`，于是 `categories` 保持空数组；
2. 界面表现是"分类栏只有全部"，看起来像**数据没配**，而不像**路径错了**；
3. 类名 `AppProductCategoryController` 和路径 `/app/product/category`
   长得太像，凭印象写下去非常自然。

**修法**：把路径改成 `/app/product/category/list`。

顺带一个收获：这个路径**不需要登录**——因为 `SaTokenConfig` 里有
`/app/product/**` 白名单，而 `/app/product/category/list` 正好匹配。
所以分类导航在未登录时也能加载。

> **四条教训**：
> 1. **接口路径必须去读 `@RequestMapping` 注解，不能按类名/文件名推断。**
>    类名是给人看的，路径是给 HTTP 用的，两者没有任何约束关系。
> 2. **404 和"空数组"在页面上长得一模一样。** 判 `statusCode !== 200` 之后
>    至少要 `console.warn` 出实际状态与响应体，否则排查时连"请求是否成功"都无法确认。
>    我这次的代码只写了 `return`，等于把证据丢掉了。
> 3. **后端日志比前端现象可靠。** 前端只告诉你"少了两项"，
>    后端日志直接告诉你"资源不存在 | app/product-category/list"。
>    遇到"数据没出来"先翻后端日志的 `uri=`。
> 4. **`/product/category` 和 `/product-category` 是两条完全不同的路径。**
>    带连字符的是类名风格，带斜杠的是 REST 资源层级风格 ——
>    这个项目里两种都有，接线时必须逐个核对。

### 40. 后台里的图片全部「加载失败」—— vite 没代理 /files

**现象**：商品编辑弹窗里的封面图位置显示 **「加载失败」**，
商品列表的封面缩略图也是空白。

**根因**：`vite.config.ts` 只代理了 `/admin`：

```ts
proxy: {
  '/admin': { target: 'http://127.0.0.1:8080', changeOrigin: true }
}
```

而后端把上传的图片存成**相对路径** `/files/product/1.png`（这是对的：
写死域名后换机器、换端口、上云托管，库里的图片就全挂了）。
浏览器拿到 `/files/product/1.png` 会向**当前源**请求，也就是

```
http://127.0.0.1:5173/files/product/1.png
```

5173 是 vite dev server，它只认识源码和打包产物。更坑的是：
**它不会返回 404，而是返回 `index.html` 并带上 HTTP 200**
（Vite 的 SPA fallback：任何不认识的路径都当成前端路由）。
浏览器拿到一段 HTML 却要当图片渲染 → 裂图 /「加载失败」。

所以排查时看到的不是"文件不存在"，而是"图片坏了"。

**修法**：给 vite 也加上 `/files` 代理。生产环境用 Nginx 同样要配这一条。

> **两条教训**：
> 1. **相对路径的图片必须保证"当前源能取到它"。** 后端返回 `/files/x.png`
>    是正确设计，但前提是前端 dev server / Nginx 要把 `/files` 转发给后端。
>    否则前端会拿自己的 SPA fallback 去响应，得到 200 + HTML。
> 2. **HTTP 200 不代表拿到的是图。** 判断图片是否正常要看 `Content-Type`。
>    我这次的验证方式就是 `curl -w '%{http_code}|%{content_type}|%{size_download}'`，
>    一眼就能看出"200 但返回的是 html"。

### 41. 商品轮播图永远只有一张 —— 子类重载被父类签名抢走了

**现象**：在管理后台给商品填了 3 张轮播图，数据库 `images` 列确实是 3 张的 JSON，
但小程序商品详情页的轮播只有 **1 张**（而且就是封面图）。
没有任何报错，接口返回 200。

**根因**：一个很隐蔽的 Java 重载解析问题。

```java
public class ProductDetailVO extends ProductVO {   // 子类
    private List<String> images;                   // ← 图片解析成数组
}
public class ProductVO {                            // 父类
    private String imagesRaw;                      // ← 原始 JSON 字符串
}

// 小程序 VO 的转换方法，只接受父类
public static ProductAppVO from(ProductVO source) {
    vo.setGallery(buildGallery(source.getImagesRaw(), source.getCoverUrl()));
}
```

详情接口写的是：

```java
ProductAppVO.from(productService.detail(id))   // detail() 返回 ProductDetailVO（子类）
```

**子类可以隐式转成父类**，所以这行代码在编译期就绑定了 `from(ProductVO)`。
而 `ProductDetailVO` 只填了自己的 `images`，父类的 `imagesRaw` 是 **null** ——
于是 `buildGallery(null, coverUrl)` 一路退回"只有封面图"。

**为什么长期没被发现**：之前所有商品都只有一张封面图，
`gallery = [coverUrl]` 恰好是**正确结果**。直到真的填了多图，问题才暴露。

**修法**：加一个参数类型更具体的重载，让编译期选中它：

```java
public static ProductAppVO from(ProductDetailVO detail) {
    ProductAppVO vo = from((ProductVO) detail);              // 先复用通用字段
    vo.setGallery(buildGalleryFromList(detail.getImages(), detail.getCoverUrl()));
    return vo;
}
```

> **四条教训**：
> 1. **父类签名的方法接收子类实例时，最容易漏掉子类独有的字段。**
>    尤其是"子类加了一个同义但类型不同的字段"（`images` vs `imagesRaw`），
>    出错后表现是"数据少了一部分"，而不是异常。
> 2. **"一直正常"可能是"恰好正确"。** 单图商品的 `gallery=[封面]` 与 bug 行为完全一致，
>    所以这个 bug 在单图场景下**永远不会暴露**。要验证多值场景，必须真的造出多值数据。
> 3. **加更具体的重载，而不是在通用方法里写 `instanceof`。**
>    重载在编译期决定，意图明确；`instanceof` 是运行时分支，容易越积越多。
> 4. **同一个概念维护两套字段（`images` / `imagesRaw`）时，要明确谁是权威。**
>    这里 `ProductDetailVO.images` 权威、`ProductVO.imagesRaw` 只在列表场景权威，
>    两边的转换都必须显式处理。

### 42. 后台菜单「回收品类」没有图标 —— 因为库里写的图标名不存在

**现象**：管理后台侧边栏「商品管理」下面三项：

```
▦  分类管理
🏪 商品列表
   回收品类     ← 文字前面空了一块，没有图标
```

**根因**：`sys_permission.icon` 这一列写的是 `Recycle`，而
**Element Plus 的 293 个图标里没有叫 `Recycle` 的**。

前端渲染方式是：

```vue
<el-icon><component :is="menu.icon" /></el-icon>
```

Vue 对**不存在的组件名不报错**，只是渲染成空 —— 于是那一行就"文字前面少一块"。
编译通过、页面无异常、控制台干净。

这类问题在本项目已经出现第二次了（第一次是小程序里
`nqx-icon name="layout-grid"`，同样静默渲染成空白）。

**修法**：把 `Recycle` 改成 `PriceTag`（「回收品类」这个页面管的是

**同时补了一个校验脚本** `scripts/audit-menu-icons.js`：

```
node scripts/audit-menu-icons.js
```

1. 从已安装的 `@element-plus/icons-vue` 里读出**真实的** 293 个图标名；
2. 查 `sys_permission` 里所有菜单节点的 `icon`；
3. 逐个比对，报出"不存在"的那些，并给出确认有效的候选清单。
   有无效图标时退出码为 1，可接进 CI。

修好后的输出：

```

```

**写脚本时又踩了一个小坑**：`mysql --batch` 默认会把结果里的特殊字符
**转义后再输出** —— 真实的 Tab 会变成字面的 `\t`。于是 `split('\t')` 完全切不开，

> 1. **字符串型的"资源引用"（图标名、枚举值、组件名）必须校验。**

> 3. **校验脚本的数据源要用 `require`/API，不要正则解析打包产物。**
>    我试过解析 `.d.ts` 和 `index.js`，都匹配不到导出名（打包后写法不统一）。
> 4. **命令行工具的默认输出可能被转义。** `mysql --batch` 会转义 Tab/换行，
>    `mysqldump` 会加注释与条件语句 —— 拿它们做机器解析前，
>    先确认有没有 `--raw` / `--skip-comments` 这类开关。

### 43. 只看「BUILD SUCCESS」就宣布改完了 —— 但 .bat 启动链路早断了

**现象**：改完一批代码，编译通过、前端构建通过、接口用 curl 直连 8080 也正常，
于是宣布"改好了"。用户回来后打不开管理后台 —— 因为**启动方式不是 curl**。

**根因**：我的验证方式和用户的验证方式不是同一条链路。

| 我验证的 | 用户实际用的 |
|---|---|
| `mvn package` → BUILD SUCCESS | 双击 `启动全部.bat` |
| `curl http://127.0.0.1:8080/...` 直连后端 | 浏览器开 `http://127.0.0.1:5173`（走 **vite 代理**） |
| 用 admin token 直接打接口 | 页面里 axios 拿 token 再打接口 |

两者差了两个环节：**启动脚本**和 **vite 代理**。而这两处恰恰最容易被我改坏：

- 改了 `vite.config.ts`（比如加 `/files` 代理）→ **必须重启 dev server 才生效**，
  而 `启动管理后台.bat` 才负责重启它；我直接 curl 后端当然看不出问题；
- 加了新依赖、某个 Bean 初始化失败 → 后端**启动即失败**，
  而我如果只跑 `mvn package`，编译是过的；
- 菜单图标名写错 → 编译通过、接口 200、页面无报错，只是图标位置空白。

**这不是技术问题，是流程问题：我用了一条用户不会走的验证路径。**

**修法**：写了 `scripts/verify-local.ps1` + `检查本地.bat`，
用**真实 HTTP** 把用户会走的那条链路整个走一遍：

```
1. 后端 /actuator/health = UP
2. 管理后台 5173 首页返回 HTML
3. 经 5173 代理登录拿 token        ← 同时验证 vite proxy
4. 菜单数与图标数一致              ← 图标名不存在会静默变空白
5. 经 5173 取 /files/product/1.png ← 验证相对路径图片链路
6. 上传接口返回形态与存储模式匹配   ← local 出 /files/，cos 出 https 且能打开
7. 小程序 37 个 JS 文件语法
```

跑一次 10 秒，7 项 PASS/FAIL，退出码可直接接 CI。

**顺手还抓到一个输出 bug**：脚本最后一行写的是

```powershell
Write-Output ' 可以打开 http://127.0.0.1:' + $FrontendPort + ' 使用'
```

PowerShell 把 `'a' + $b + 'c'` 当成**多个参数**传给 `Write-Output`，
于是输出被拆成了五行：`可以打开…` / `+` / `5173` / `+` / `使用`。
正确写法是双引号插值或加括号。**这种错编译不报、运行不报，只是排版难看** ——
又是"只能靠看一眼真实输出"才能发现的问题。

> **四条教训**：
> 1. **验证路径必须和用户的使用路径一致。** 用户双击 bat，你就得跑 bat；
>    用户走 5173，你就不能只 curl 8080。
> 2. **"编译通过"只能证明语法对，证明不了能启动。** Bean 初始化失败、
>    配置缺失（如 COS 密钥）、端口冲突都发生在**启动阶段**。
> 3. **把手工验证固化成脚本。** 手工验证有两个问题：会忘、会挑好走的路走。
>    写成脚本之后，每次都是同样的 7 项，跑 10 秒，不会自欺欺人。
> 4. **改了配置文件必须重启对应进程。** `vite.config.ts` 的热更新不生效、
>    `.env` 要重启容器、`application.yml` 要重启应用 —— 这类"改了不生效"
>    占排查时间的比例出乎意料地高。

### 44. 导出功能在云托管上一定失败 —— 网关把响应截断了

**现象**：本地导出 Excel 一切正常。部署到微信云托管后，点导出——
浏览器显示"下载完成"，但用 Excel 打开提示**"文件已损坏"**。

**根因**：云托管对返回包有 **1000KiB 上限**：

> 请求大小限制 100KiB，返回包大小限制 1000KiB。
> —— [微信小程序访问云托管服务](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/development/call/mini.html)

而原来的实现是把 xlsx **直接写进 HTTP 响应流**（`responseType: 'blob'`）：

```java
FastExcel.write(response.getOutputStream(), clazz).sheet(name).doWrite(rows);
```

订单导出一多，xlsx 就超过 1MB → 响应被截断 → 前端拿到半个文件。
**而且这个失败方式是"静默成功"**：浏览器认为下载完成了，用户打开才发现坏。

**修法**：改成「生成 → 存对象存储 → 返回下载链接」：

```
旧：GET /admin/order/export → 200 + 几 MB 的 xlsx 二进制
新：GET /admin/order/export → 200 + {"code":200,"data":"/files/export/...xlsx"}
    GET <data 里的地址>       → 200 + xlsx
```

实测对比：**接口响应 125 字节，文件本身 4082 字节** —— 彻底绕开限制。

顺带改进了两点：

1. **文件名有意义了**。对象 key 里带上 sheet 名 + 时间戳
   （`订单列表_20261020161219.xlsx`），不再是 UUID；
   同一个链接下载两次也不会互相覆盖。
2. **链接可以重复使用**。一次性流发出去就找不回来了，
   而链接可以再打开、可以发给别人。

**前端也要跟着改**：`<a download>` 的 `download` 属性**只对同源生效**。
本地模式（`/files/...` 同源）文件名能生效；COS 模式（跨域）会被忽略，
所以后端把有意义的名字放进了对象 key。另外要加 `target="_blank"`，
否则跨域时浏览器会**导航**到文件地址，把当前页面顶掉 ——
用户会以为"点导出把系统点没了"。

> **三条教训**：
> 1. **部署环境的网关限制要提前查。** 请求体 100KiB、返回包 1000KiB、
>    timeout 15 秒 —— 这三条会直接决定"哪些功能要换实现方式"，而不是上线后再发现。
> 2. **"大文件走响应流"在网关后面天然不可靠。** 只要前面有一层网关/代理，
>    就该假设它会对响应体做限制。改成"文件单独下载"是最省事的规避方式。
> 3. **静默成功比报错更危险。** 浏览器说"下载完成"、用户打开发现坏了，
>    这种体验比直接报错糟糕得多 —— 而且用户会归因到"这个系统坏了"。

### 45. 给 profile 配置加一段，结果写出了两个顶层 `spring:` 键

**现象**：往 `application-prod.yml` 里加静态资源配置，本地构建能过（`mvn package`
不解析 YAML），但应用**启动就失败**，而且报错信息指向莫名其妙的地方。

**根因**：文件里出现了**两个顶层 `spring:` 键**：

```yaml
spring:                    # ← 第一个（原本就有）
  datasource: ...

nqx:
  upload: ...

spring:                    # ← 第二个（我新加的）
  web:
    resources:
      static-locations: file:/app/static/
```

YAML 规范里重复键是**错误**，SnakeYAML 默认会拒绝。而 Spring Boot 的报错
通常只说"加载配置失败"，不会直接告诉你"第 95 行有个重复的 spring"。

**为什么容易犯**：往一个已经很长的配置文件**末尾追加**一段新配置时，
很自然地会写一个顶层键，而没有回头确认那个键是否已经存在。

**修法**：把 `web:` 并进已有的 `spring:` 块里。

**顺带还犯了第二个错**：用行内编辑删空行时，把 `driver-class-name` 那行
和下一行的 `url:` 拼成了一行：

```yaml
    driver-class-name: com.mysql.cj.jdbc.Driver    url: jdbc:mysql://...
```

这会让 `url` 变成一个字符串值的一部分 —— datasource 失去 URL，
启动时报"无法确定数据库类型"。**行内编辑删除换行是很危险的操作。**

**加了一个静态检查**（现在手工跑）：

```powershell
# 顶层键是否唯一
Select-String -Path app*.yml -Pattern '^[a-zA-Z]' | ForEach-Object { $_.Line.TrimEnd(':') } | Group-Object | Where-Object { $_.Count -gt 1 }
```

> **三条教训**：
> 1. **`mvn package` 通过 ≠ 配置正确。** YAML/属性文件是在**运行时**解析的，
>    构建阶段完全不碰。改完配置必须真的启动一次。
> 2. **往长配置文件追加内容时，先看一眼顶层键有没有重复。**
>    这是 YAML 特有的坑：JSON 里重复键会被后者覆盖（静默），YAML 里直接报错。
> 3. **删空行/换行要用"整行删除"，不要用手工拼接。** 行内编辑很容易把两行粘在一起，
>    而粘连后的 YAML 依然"能解析"，只是语义完全变了 —— 这比语法错误更难查。

### 46. `docker compose up` 卡在 Redis 不健康 —— healthcheck 读了一个没人设置的变量

**现象**：`docker compose -p nqx up -d` 之后，MySQL 很快变成 `healthy`，
但 Redis 一直是 `unhealthy`，应用容器**根本不启动**（`depends_on: service_healthy`）。

```
Container nqx-mysql Healthy
Container nqx-redis Error dependency redis failed to start
dependency failed to start: container nqx-redis is unhealthy
```

**排查**：直接看容器的健康检查输出：

```powershell
docker inspect nqx-redis --format "{{json .State.Health}}"
```

```
"AUTH failed: WRONGPASS invalid username-password pair or user is disabled."
```

**根因**：healthcheck 写的是

```yaml
test: [ "CMD-SHELL", "redis-cli -a $$REDIS_PASSWORD ping | grep PONG" ]
```

`$$` 在 Compose 里表示「保留成字面 `$`，交给**容器内的 shell** 展开」，
也就是读**容器内的环境变量** `REDIS_PASSWORD`。

可是 compose 从来没给 redis 容器设过这个变量 —— 上面 `command` 里的
`${REDIS_PASSWORD:-123456}` 是**Compose 在解析阶段就替换掉的**，
替换完就没了，不会进入容器环境。

于是实际执行的是 `redis-cli -a ""` → 用空密码认证 → `WRONGPASS` → 永远不健康。

**修法**：显式给容器注入该变量

```yaml
environment:
  REDIS_PASSWORD: ${REDIS_PASSWORD:-123456}
```

顺带加了 `--no-auth-warning`，否则每 10 秒往日志里打一行"用 -a 传密码不安全"。

**为什么这么久没发现**：这个 `docker-compose.yml` 之前从来没被真正跑起来过。
写了、看起来合理、但没验证 —— 和"只看 BUILD SUCCESS"是同一类问题。

> **三条教训**：
> 1. **`$$` 和 `${}` 在 compose 里含义完全不同。** `${VAR}` 是 Compose 解析期替换
>    （结果进 `command`/`environment` 的字面值）；`$$VAR` 是留给容器内的 `$VAR`。
>    想「把变量传给容器」必须走 `environment:`，不能只写在 `command:` 里。
> 2. **健康检查失败时，先看 `docker inspect ... .State.Health`。**
>    它直接给出失败命令的输出，比猜快得多 —— 本次一次就定位到 `WRONGPASS`。
> 3. **`depends_on: service_healthy` 会把上游的不健康变成下游的"完全不启动"。**
>    好处是避免应用在半坏的环境里启动；坏处是症状出现在**另一个容器**上，
>    容易误以为是应用本身的问题。
