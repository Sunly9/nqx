## 1. 阶段划分与验收标准

每个阶段都要求「**可启动 + 可演示 + 可验收**」，不允许出现做完一大块才第一次运行的情况。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 地基** | 建库建表、多模块骨架、统一返回/异常/日志、Sa-Token 双端登录、三级 RBAC | 后台用 admin 能登录并拿到动态菜单；用审核员账号登录只看到 3 个菜单；接口无权限返回 403 |
| **P1 商品域** | 商品/分类/回收品类 CRUD、文件上传、小程序端浏览 | 后台能增删改查商品并上下架；小程序能分页浏览、看详情 |
| **P2 订单域** | 购物车、地址、下单、**状态机**、流转日志、**延迟队列超时取消**、模拟支付 | 下采购单不支付 → 30 分钟后自动关闭；回收单全流程走完并生成流转日志 |
| **P3 积分域** | 积分账户/流水、答题发积分、积分兑换、**幂等 + 并发扣减**、**Redis 缓存** | JMeter 200 并发兑换不超卖、不超发、不漏单；缓存命中率可观测 |
| **P4 问答域** | 每日问答、答题记录、防重复作答、后台题库多条件检索 | 同一题重复提交被拦截；后台按题型/难度/时间组合检索正确 |
| **P5 管理后台** | Vue3 + Element-Plus + 动态路由 + 按钮级权限 + ECharts 看板 | 三种角色登录看到的菜单与按钮不同；看板图表数据与数据库一致 |
| **P6 小程序端** | request 封装、401 静默重登、分包加载、全部业务页面 | 商家工具真机预览通过，token 过期能自动恢复 |
| **P7 交付** | Docker Compose、README、压测报告、简历/面试要点整理 | `docker compose up -d` 后无需任何手工操作即可访问 |

## 3. 关键技术难点的落地方案

### 3.1 订单状态机（策略模式 + 状态流转表）

```java
// 1) 状态枚举：两套状态机共用一套枚举，用 orderType 区分语义
public enum OrderStatusEnum {
    PENDING_AUDIT((short) 10, "待审核"),
    AUDIT_PASSED((short) 11, "审核通过/待回收"),
    // ...
}

// 2) 流转动作枚举
public enum OrderActionEnum { SUBMIT, AUDIT_PASS, REJECT, CANCEL, CONFIRM_RECYCLE, SETTLE, PAY, DELIVER, CONFIRM, TIMEOUT }

// 3) 状态机：定义「哪种订单类型下，哪些 (当前状态 -动作-> 目标状态) 是合法的」
@Component
public class OrderStateMachine {
    private final Map<Integer, Map<OrderStatusEnum, Map<OrderActionEnum, OrderStatusEnum>>> rules;

    public OrderStatusEnum next(OrderTypeEnum type, OrderStatusEnum current, OrderActionEnum action) {
        OrderStatusEnum target = rules.getOrDefault(type.getCode(), Map.of())
                .getOrDefault(current, Map.of())
                .get(action);
        if (target == null) {
            throw new BizException(ErrorCode.ORDER_STATUS_ILLEGAL);  // 非法流转直接拒绝
        }
        return target;
    }
}

// 4) 策略模式：不同类型订单的处理差异
public interface OrderHandler {
    OrderTypeEnum supportType();
    String createOrder(OrderCreateDTO dto);
    void onPaid(BizOrder order);
}
@Component class RecycleOrderHandler implements OrderHandler { ... }
@Component class PurchaseOrderHandler implements OrderHandler { ... }
// 用 Map<Integer, OrderHandler> 注入，按 orderType 分发，彻底消灭 if-else
```

**为什么值得做**：所有状态变更都要经过状态机校验，非法流转（比如「已完成」的订单又被取消）在入口就被拦住；流转成功后统一写 `order_flow`。**讲这一块能讲 15 分钟不重样。**

### 3.2 订单超时自动取消（Redis ZSet 延迟队列）

```
下单     → ZADD delay:order <超时时间戳> <orderNo>
定时任务 → 每秒 ZRANGEBYSCORE delay:order 0 <now> LIMIT 0 20
         → 对每个 orderNo 用 Lua 脚本原子地 ZREM（返回 1 才说明抢到了这条消息）
         → 查订单状态，仍是「待支付」才关闭，否则忽略（已支付/已取消）
         → 关闭订单 + 回滚库存 + 写流转日志
```

**三个必须讲清的点**：
1. **为什么要 `ZREM` 成功才处理**：多实例部署时定时任务会并发抢同一条消息，`ZREM` 的返回值是天然的分布式互斥锁，比额外加分布式锁更轻。
2. **为什么处理时要再查一次状态**：延迟消息存在「到点但订单已经支付了」的正常竞态，必须做**幂等校验**。
3. **兜底**：定时任务本身可能挂掉或被重启错过时间窗，所以再加一个「每 5 分钟扫描 `status = 待支付 AND create_time < now - 30min`」的补偿任务。**主动说出兜底方案是加分项。**

### 3.3 积分并发与幂等 → 见 [`02-数据库设计说明.md` 第 6 节](02-数据库设计说明.md#6-积分的并发与幂等核心难点)

### 3.4 商品热点缓存（Cache-Aside + 逻辑过期）

```
读：先查 Redis
   ├─ 命中且未逻辑过期 → 直接返回
   ├─ 命中但已逻辑过期 → 尝试获取互斥锁
   │     ├─ 拿到锁 → 开异步线程重建缓存，当前请求先返回旧数据（保证可用性）
   │     └─ 没拿到 → 直接返回旧数据
   └─ 未命中（穿透风险）→ 获取互斥锁 → 查库
         ├─ 库里有 → 写缓存（过期时间加随机值防雪崩）→ 返回
         └─ 库里没有 → 缓存空对象，短过期时间（防穿透）
写：先更新数据库 → 再删除缓存（Cache-Aside）
```

**缓存三兄弟的标准答案**（面试必问，要能脱口而出）：

| 问题 | 现象 | 本项目解法 |
|---|---|---|
| 缓存穿透 | 查不存在的数据，请求全打到库 | 空值缓存（短期） / 布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间，大量请求同时打库 | 互斥锁重建 / **逻辑过期**（不设 TTL，靠业务字段判断） |
| 缓存雪崩 | 大量 key 同时过期 | 过期时间加随机值；缓存集群高可用 |

**一致性**：项目里用「先更库再删缓存」，并说明其理论缺陷（删缓存失败 → 脏数据）与改进方向（延迟双删 / Canal 订阅 binlog 异步删除）。**能指出自己方案的不足，比声称方案完美更能拿分。**

### 3.5 接口幂等（`@Idempotent` 注解 + AOP + Redis）

```java
@Idempotent(prefix = "order:submit", key = "#dto.userId", expire = 10)
@PostMapping("/purchase")
public Result<String> submitPurchase(@RequestBody @Valid OrderCreateDTO dto) { ... }
```

```
AOP 环绕：
  key = prefix + ":" + SpEL 求值结果（或直接取请求 token / MD5(请求体)）
  Boolean ok = redis.opsForValue().setIfAbsent(key, "1", expire, SECONDS)
  if (!ok) throw new BizException(ErrorCode.REPEAT_SUBMIT);
  try { return pjp.proceed(); }
  catch (Exception e) { redis.delete(key); throw e; }   // 失败要释放，否则用户无法重试
```

### 3.6 操作日志（`@Log` 注解 + AOP + 异步落库）

```java
@Log(module = "订单管理", operation = "审核回收订单")
@PostMapping("/{orderNo}/audit")
public Result<Void> audit(@PathVariable String orderNo, @RequestBody AuditDTO dto) { ... }
```

AOP 记录：操作人（从 Sa-Token 取）、方法、URL、**脱敏后的入参**（`password`、`phone` 必须打码）、响应、IP、耗时、异常。
落库用 `@Async` + 独立线程池，避免拖慢主流程；线程池要 `ThreadPoolTaskExecutor` 自定义（核心线程数、队列容量、拒绝策略），**并把 Sa-Token 上下文 / traceId 通过 `TaskDecorator` 传递到子线程**——这是个很容易被忽略、但面试官很喜欢的细节。

### 3.7 统一 traceId 链路追踪

`OncePerRequestFilter` 生成/透传 `traceId` 放入 MDC，logback pattern 里输出 `[%X{traceId}]`，异步线程用 `TaskDecorator` 复制 MDC。**一次请求的所有日志可以用一个 traceId 串起来**，这是"工程化"的直接体现。

| POST | `/app/repair/apply` | 提交维修申请（返回 `type=warranty/paid`） | 登录 |
| GET | `/app/repair/list` | 我的维修申请列表 | 登录 |
| GET | `/app/repair/{id}` | 维修申请详情 | 登录 |
| GET | `/admin/order/{orderNo}/actions` | **下发当前订单可执行的动作** | `order:recycle:list` 或 `order:purchase:list` |

### 5.3 两处值得单独说明的设计

**① `/admin/order/{orderNo}/actions` 是为了消除"前后端各维护一份状态机规则"**

没有它的时候，前端要自己写一份映射表决定"这个状态下该显示审核通过还是驳回还是确认回收"。
一旦后端调整状态机（新增状态、改变流转条件），前端的映射表不会自动跟着变，
用户就会看到一个点了就报"当前状态不允许该操作"的按钮。
把状态机的判断结果直接下发，**规则的唯一来源留在后端**，这类不一致从根上消失。

**② `/admin/order/page` 的权限注解用了 OR 语义**

```java
@SaCheckPermission(value = {"order:recycle:list", "order:purchase:list"},
                   mode = SaMode.OR, type = "admin")
```

这是一个接口服务两类订单（按 `orderType` 区分），但菜单与角色是按
「回收订单」「采购订单」分别授权的。若只写 `order:recycle:list`，
一个"只管采购"的角色会**看到采购订单菜单、点进去却直接 403** ——
菜单可见但页面不可用，是最让人困惑的一类权限问题。

### 5.4 维护建议

- 新增接口时**同步更新本节**，而不是回头改第 2 节的规划（规划记录的是当时的判断，有史料价值）；
- 权限码必须与 `sys_permission` 表一致，改完跑一次
  `scripts/check-permissions.ps1` —— 权限码是字符串字面量，与数据库之间没有编译期约束，
  拼错时编译通过、启动通过，只有调用时才 403（这个坑真实发生过一次，见 [docs/06 §23](06-踩坑记录.md)）。

## 6. 明确不做的事（控制范围，避免样样半成品）

| 不做 | 原因 |
|---|---|
| 真实微信支付 | 需求已明确为模拟结账，保留 `pay_type` + `PayService` 接口扩展点即可 |
| Nacos / 网关 / 微服务拆分 | 单体足够，硬上微服务但讲不清反而是减分项 |
| ShardingSphere 分库分表 | 无真实数据量支撑，讲不出取舍就是堆技术栈 |
| ElasticSearch 商品搜索 | `LIKE` + 索引足够，量级不到 |
| Seata 分布式事务 | 单库单服务，引入它属于自找麻烦 |
| 富文本编辑器（商品详情） | 用 Markdown/纯文本降级，把时间留给核心难点 |
