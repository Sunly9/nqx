## 3. 三个必须知道的发现

### 3.1 ❌ 放弃 Knife4j —— 它在 Spring Boot 3.5 上是硬性不兼容

**这是本次核查最重要的结论，避免了一个会在运行期才爆发的坑。**

**证据链**：

1. `knife4j-openapi3-jakarta-spring-boot-starter` 的最后版本是 **4.5.0**（2024-01），此后官方再无发布。
2. 读 [`knife4j-4.5.0.pom`](https://repo1.maven.org/maven2/com/github/xiaoymin/knife4j/4.5.0/knife4j-4.5.0.pom) 的 parent，发现它把 `knife4j-springdoc-openapi-jakarta.version` **硬锁在 `2.3.0`**。
3. springdoc 2.3.0 早于 Spring Framework 6.2，而 Spring Boot 3.5.16 使用的是 Spring Framework **6.2.19**。
4. 版本错配导致运行期异常：

```
java.lang.NoSuchMethodError:
  'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'
```

**注意这个错误发生在运行期，不是编译期**——`mvn compile` 会成功，启动时才炸。这是最浪费时间的一类问题。

**网上的"绕过方案"不可取**：排除 springdoc 依赖后单独引 2.8.x、同时设 `knife4j.enable=false` —— 这样虽然能启动，但 **Knife4j 的文档访问密码验证会被一并绕过**，等于把接口文档裸奔在生产环境。

**✅ 采用方案**：直接用 `org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.17`。
它的 parent 就是 `spring-boot-starter-parent:3.5.13`，属于官方自己验证过的组合。访问地址：`/swagger-ui.html`、`/v3/api-docs`。

> **Knife4j 与 springdoc 2.8.17 绝不能共存**。若启动时看到 `ControllerAdviceBean` 相关报错，第一反应就是检查是否被间接引入了 Knife4j。

### 3.2 MyBatis-Plus 的最低可用版本是 3.5.16

逐个阅读每个 starter 的 pom，看它内部导入的 `spring-boot-dependencies` 版本：

| MyBatis-Plus | 内部导入的 spring-boot-dependencies | 判断 |
|---|---|---|
| 3.5.9 | 3.3.4 | 落后 Boot 3.5 两个小版本 |
| 3.5.12 | 3.4.1 | 落后 |
| 3.5.13 / 3.5.14 / 3.5.15 | 3.4.1（mybatis-spring 3.0.5） | 落后 |
| **3.5.16** | **3.5.9** | ✅ **唯一显式对齐 Boot 3.5 的版本** |

**结论**：配 Spring Boot 3.5.16 时，MyBatis-Plus **必须 ≥ 3.5.16**，否则可能因 BOM 版本冲突出现自动配置失效或运行时 `NoSuchMethodError`。

## 4. 已知风险与落地验证清单

### 4.1 风险 1：Spring Boot 3.5.x 的免费支持已终止

**事实**：Spring Boot 3.5.x 的开源免费支持于 **2026-06-30** 结束，3.5.16 是 3.5 线终点，之后仅提供商业支持。下一个长期支持线是 4.x。

**本项目的决策：仍然使用 3.5.16，理由如下**：

1. 这是**求职作品项目**，不是生产系统，不会面临真实的安全攻击面；
2. 用户的核心诉求是「最稳定、最不会出现版本不兼容」，而 3.5.16 的生态适配是**经过验证的**——MyBatis-Plus 3.5.16 显式对齐、springdoc 2.8.17 的 parent 就是 Boot 3.5.13、Redisson 3.52.0 官方针对 3.5.5 构建。这些都是在 POM 里读到的硬证据；
3. 迁移到 Boot 4.x 意味着**上述每一项都要重新核查验证**，而这些验证成本会挤占本该用于打磨核心难点（状态机、幂等、缓存一致性）的时间；
4. 现实情况是，国内大量企业生产环境仍运行在 2.7 / 3.2 等更早的版本上，**用 3.5.x 在求职场景中完全不会显得落后**。

**如果安全补丁是硬需求**：整体迁 Boot 4.x，并重跑一遍本文件的核查流程，重点是确认 MyBatis-Plus / Sa-Token / springdoc 是否已发布 Boot 4 适配版本。

### 4.2 风险 2：FastExcel 的传递依赖与 Boot 冲突

`fastexcel:1.3.0` 传递依赖：
- `slf4j-api:1.7.36` —— 与 Boot 3.5.16 的 `2.0.18` **二进制不兼容**。Maven 的 dependencyManagement 会覆盖为 2.0.18，但**必须验证**。
- `ehcache:3.9.11` —— 可能干扰 Boot 的 `CacheManager` 自动选择。

```bash
# 必须在 POM 写完后执行
mvn dependency:tree -Dincludes=org.slf4j
mvn dependency:tree -Dincludes=org.ehcache
```

若出现 `slf4j-api:1.7.36`，需在 `<dependencyManagement>` 中显式钉死版本。

### 4.3 风险 3：MapStruct + Lombok 注解处理器顺序

配置不当会导致 MapStruct **静默生成空实现**——编译能通过，但运行期转换出来的对象所有字段都是 `null`，是最难排查的一类问题。

**正确的 `annotationProcessorPaths` 顺序（顺序不能错）**：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <!-- 1. Lombok 先执行，生成 getter/setter -->
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>${lombok.version}</version>
            </path>
            <!-- 2. binding 负责让 MapStruct 看到 Lombok 生成的访问器 -->
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok-mapstruct-binding</artifactId>
                <version>${lombok-mapstruct-binding.version}</version>
            </path>
            <!-- 3. 最后才是 MapStruct -->
            <path>
                <groupId>org.mapstruct</groupId>
                <artifactId>mapstruct-processor</artifactId>
                <version>${mapstruct.version}</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
```

**验证方法**：写一个最简转换器单测，断言转换后对象非 `null`。

### 4.4 风险 4：PageHelper 与 MyBatis-Plus 互斥

`pagehelper-spring-boot-starter` 强依赖原生 `mybatis-spring-boot-starter`，与 MyBatis-Plus 的自动配置互斥，**不引入**。分页统一使用 MyBatis-Plus 的 `IPage` / `Page`。
